# Reviewed legacy unique-index repair

This administrator-only tool repairs only these established natural keys:

| Table | Intended UNIQUE key |
| --- | --- |
| `online_products` | `uk_online_products_shop_sku(shop_id, ozon_sku)` |
| `order_status_history` | `uk_order_status_history_hour_state(order_id, observed_hour, status, logistics_status, tracking_stage, sync_state)` |
| `ozon_category_mappings` | `uq_ozon_category_mapping(description_category_id, type_id)` |

The October 22 backup contains distinct primary rows violating these keys. The current production global `unique_checks` and `foreign_key_checks` are enabled. The historical cause has not been established. Keeping all dump rows by downgrading these three indexes produces a data-exact recovery clone, with `schema_exact=false`; it does not itself repair production.

## Scope and safeguards

`scripts/repair-reviewed-unique-indexes.mjs` defaults to read-only inspection. Both `--database` and `--mysql-admin-socket` are mandatory; application configuration is never imported. Audit starts a READ ONLY transaction, uses a ten-second per-SELECT execution limit, and only inspects explicit primary IDs. Duplicate discovery over the complete history table belongs on the isolated recovery clone, not the live service. Output contains IDs, fingerprints, differing column names and refusal reasons; SQL errors are redacted because MySQL can include private SKU values in duplicate-key messages.

Plans explicitly list each group, keeper, all inspected row hashes, accepted differing columns, reference digest, reviewer and reason. IDs beyond JavaScript's safe integer range must be JSON strings. The suggested keeper is advisory. Online keepers must retain each group's unique effective product/Ozon identity; different nonempty identities are refused, even if there are no current references. Category keepers must remain active and retain positive official category/type IDs. `is_auto` describes category classification and is not an authorization or trust signal.

All ownership checks resolve legacy NULL ownership only to the actual default enterprise. Shops, inventory products and order-item parents must agree. Unknown typed references, FK relationships, triggers, generated/invisible columns, or unexpected key definitions require separate review. Existing malformed parent relationships fail closed; the tool does not silently repair historical business relationships. The single explicit preservation case below retains an unresolved relationship without claiming it has been corrected.

### One unchanged outbound relationship pending business review

An optional `unchanged_outbound_reference` object permits retaining **one exact existing `outbound_records` row** when its current order-item parent's shop differs from its online-product shop but both shops belong to the same actual enterprise. It is not an exception list or a parent-repair instruction. All fields are mandatory: `table:"outbound_records"`, `row_id`, `shop_id`, `online_product_id`, `order_item_id`, `expected_parent_order_id`, `expected_parent_shop_id`, `expected_tenant_id`, `expected_full_row_sha256`, `user_confirmation_reference` and `reason`. IDs follow the normal precision-safe integer rules; the confirmation must describe the user's explicit decision to retain the entire unresolved record.

The online ID must already equal an explicitly reviewed duplicate-group keeper. It cannot refer to a loser or be remapped. The complete native row hash, original row/shop/item IDs, current item-to-order link, parent-order shop and actual enterprise are checked again using current locking reads in the reference transaction. Missing or changed parents, cross-enterprise ownership, invalid product bindings, changed fields, an extra malformed reference, missing approval, arrays and additional exception fields refuse execution. Only this exact row's parent-shop disagreement is bypassed; all other guards remain active. No status, quantity, amount, product binding, parent or ledger data is rewritten.

The inspect/apply/combined reports return the exact IDs, full-row SHA, one-row native before/after digests, `byte_unchanged:true` after verified preparation/application, and `relationship_reconciled:false`. The original parent relationship remains pending business reconciliation. Byte preservation and strict UNIQUE reconstruction do not establish that the original parent link represents the correct historical shipment.

The six audited SQL `online_product_id` columns reference local `online_products.id`: actions, outbound records, stock snapshots, barcode-label cache, recipes and SKU mappings. The active inventory application reference `inventory_product_requests.payload_json.online_product_id` is also migrated. Changing an inventory or external Ozon ID with a similar name is forbidden. Barcode-cache collisions require explicit invalidation; full PDF bytes and both affected cache originals remain archived. Other fields and timestamps are preserved. Action/listing/AI JSON snapshots remain historical evidence, including original source IDs; they are not numerically searched and replaced. Review stale active drafts/browser contexts before resuming work.

## Maintenance execution

Stop all application writers, workers, scheduled jobs, event-scheduler writes and administrator SQL writers. `maintenance_confirmed` is an operator acknowledgement, not an automatic server-wide write lock. A database-specific advisory lock prevents two instances of this tool, but cannot stop unrelated writers. The apply connection must have `unique_checks=1`. Keep maintenance active until independent validation and a fresh successful dump/restore finish.

1. Audit the explicit seed plan and copy the returned `expected_hashes`, `differing_columns` (as `accepted_differing_columns`) and `expected_reference_digest` into the reviewed plan. Specify a fresh twelve-character lowercase hex `repair_id`, `reviewed_by`, `reason`, `maintenance_confirmed:true` and `rollback_restores_nonunique_schema:true`. Online repair also needs `invalidate_barcode_cache:true` and `preserve_historical_json:true`.
2. Review every identity, parent/tenant and schema conflict. Any refused group blocks automatic apply. Omitting a real duplicate group does not bypass this: the shadow's real UNIQUE key rejects the copy.
3. Run audit, then apply using the same explicit database/socket and reviewed plan:

   ```text
   node scripts/repair-reviewed-unique-indexes.mjs --database=EXPLICIT_DB --mysql-admin-socket=EXPLICIT_SOCKET --plan=/absolute/reviewed-plan.json
   node scripts/repair-reviewed-unique-indexes.mjs --database=EXPLICIT_DB --mysql-admin-socket=EXPLICIT_SOCKET --plan=/absolute/reviewed-plan.json --apply
   ```

Apply builds fresh strict shadow tables from PRIMARY-index reads, excluding only reviewed nonkeepers. There is no IGNORE, REPLACE, truncation, field merging, or DELETE against an original duplicate business table. Full retained-row hashes/counts and original AUTO_INCREMENT are preserved. Every original row remains in the complete old table. A separate reference transaction locks rows and archives native complete before/after rows, then remaps only the seven audited paths. Any DML error rolls that transaction back, including cache invalidation and archive inserts.

The original broken UNIQUE is downgraded to a same-column NONUNIQUE index using in-place DDL, and the table is rehashed. This is essential: leaving a broken UNIQUE on an archive would make the next dump unrestorable. Atomic multi-table RENAME installs all fresh shadows together and retains complete originals in `_uir_<repair_id>_old_<table>`. `_reviewed_unique_index_repairs` stores the reviewed plan, original schema text, counts/hashes, artifact identities and durable phases. Before/after reference tables preserve full native data, including BLOBs.

MySQL DDL commits implicitly. Reference changes, index downgrade and table swap cannot be one SQL transaction. The journal records `preparing`, `references_applied`, `swap_pending`, `applied` and rollback phases. A failed command must leave maintenance active. Inspect the journal rather than rerunning the same repair ID:

```text
node scripts/repair-reviewed-unique-indexes.mjs --database=EXPLICIT_DB --mysql-admin-socket=EXPLICIT_SOCKET --journal=REPAIR_ID
node scripts/repair-reviewed-unique-indexes.mjs --database=EXPLICIT_DB --mysql-admin-socket=EXPLICIT_SOCKET --rollback=REPAIR_ID --maintenance-confirmed
```

Undo checks all canonical rows, original archives and complete affected reference sets against stored hashes before writing. Later changes or new affected references refuse automatic undo. It can recover after reference commit, after forward RENAME before phase persistence, and after reverse RENAME before reference restoration. Repaired tables are retained as `_uir_<repair_id>_undo_<table>`. Original data and reference bytes are restored, with the known natural keys NONUNIQUE. **Undo is data restoration with `schema_exact=false`; it cannot make the original contradictory data satisfy a valid UNIQUE or authorize restarting normal business writers.** Retain all archives/journal until reviewed backups and business verification are complete.

## Isolated verification

`test/reviewed-unique-index-repair-mysql.test.js` creates/drops only random fixture databases on the explicitly provided `TENANT_TEST_MYSQL_SOCKET`, requires TCP networking disabled, and never imports production credentials. It exercises three-table apply/undo, complete PDF/JSON restoration, strict copy failure, atomic reference rollback, identity/tenant guards, later-write refusal, read-only audit, and interrupted forward/reverse phases. No business database or production service is modified by these tests.

The 2026-10-23 full-data rehearsal exposed one MySQL rendering difference after a strict dump import: only the new `_reviewed_unique_index_repairs` journal's `repair_id`, `phase` and `state_json` declarations gained redundant explicit `CHARACTER SET utf8mb4` before the unchanged `COLLATE utf8mb4_unicode_ci`. The original failed raw-DDL comparison remains evidence. Independent review established identical complete column, index, constraint and table-option metadata, identical SQL/connection context, identical native data, and byte-identical DDL for every other table and trigger. Only those three exact named clauses were accepted as a separately reported semantic-structure equivalence; raw schema text remained unequal. Do not generalize this observation into a charset-removal rule, omit a journal from validation, alter restored DDL to fit a proof, or waive any business-table difference. A later run must retain its own raw results and independently establish any such narrowly identified equivalence.

## Combined reviewed parent correction and strict reconstruction

For a repair limited to historical order parent links and the history natural key, use the separate [history-only maintenance workflow](reviewed-history-only-repair.md). Its four-table staging scope installs only `order_status_history`; the combined coordinator below retains its fixed fifteen-table scope.

`scripts/repair-reviewed-combined-shadow.mjs` is the separate administrator coordinator for the explicitly reviewed combination of history-parent corrections, online identity/inventory decisions, reviewed outbound item corrections or the one unchanged preservation case, and the three strict natural keys. Its libraries never import application credentials or execute a standalone writing CLI. The ordinary unique-repair rollback command explicitly refuses a `mode: combined-shadow` journal; use the matching combined coordinator.

The fixed scope is fifteen tables. Only `online_products`, `order_status_history` and `ozon_category_mappings` receive complete original-table archives and strict shadow replacement. The seven documented reference tables receive native before/after images of **only changed primary rows**, followed by one reference DML transaction; the outbound item correction is in that same transaction. `tenants`, `shops`, `products`, `orders` and `order_items` remain read-only parent evidence. All fifteen are copied into an independent repair-owned staging database so the original ownership, exact candidate and typed-reference guards can run before any source installation. This staging copy does not install or archive the parent tables.

The source's three defective UNIQUE keys are never disabled for in-place history updates. Only staging downgrades those keys before the reviewed corrections. Staging then invokes the existing strict repair, retaining reviewed keeper IDs, full row hashes and accepted differing columns. A mismatched hash or identity is refused rather than replaced with a newly computed approval. Actual reference digests, changed row IDs, changed column names and native before/after fingerprints are returned for independent review. Cache deletions retain complete original PDF bytes in their before images.

The manifest requires explicit source/staging identities, separate outer/link/unique repair IDs, reviewer/reason, maintenance and NONUNIQUE rollback acknowledgements, fifteen full native row digests, original DDL and AUTO_INCREMENT counters, and the two reviewed nested plans. Read-only parent generated columns participate in full hashes but are omitted from INSERT column lists. Real generated or invisible columns on any writable target/reference, unknown typed references, unexpected primary/natural keys, and any writable-table trigger or incoming/outgoing foreign key—including an FK declared in another database—refuse preparation.

The five read-only parent tables may retain their existing triggers and FK dependencies because the coordinator never updates, deletes, alters, installs or renames those tables. Their snapshots additionally require `readonly_dependencies`: ordered trigger metadata and `SHOW CREATE TRIGGER` definitions, full FK key-column metadata plus referential rules, and a SHA-256 of those definitions. Only `information_schema.TRIGGERS.CREATED` and `SHOW CREATE TRIGGER.Created` are excluded: dump restoration necessarily recreates these server-side creation times. Every executable definition, SQL mode, definer, action order and charset/collation context remains compared; no business-row timestamp or native row hash is excluded. Source inspection, the current locked parent checks and post-install verification require exact equality to the reviewed definitions and complete parent row hashes. Definition changes refuse installation. Stage `CREATE TABLE ... LIKE` copies neither triggers nor foreign keys; actual metadata queries verify the absence on all staging tables, and no source trigger executes during copying. An external referencing table is never copied, modified or renamed.

`source_kind: production_maintenance_snapshot` requires an independently reviewed actual 64-character reference digest. Read-only inspection accepts an unapproved candidate, but preparation and installation additionally require outer `production_approved:true` as an actual boolean after independent fresh-plan review; missing, false or string approval is refused before writing. A pending digest placeholder is never accepted for production preparation or installation. Automatic placeholder resolution is confined to isolated rehearsals, where the prepared actual digest remains visible in the report. An `isolated_NONUNIQUE_backup` manifest can prepare only; it can never install. Fixture/rehearsal installation additionally requires TCP networking disabled and the exact random database-name pattern.

All application writers, workers, event-scheduler and administrator writers must remain stopped. **Capture a fresh production manifest under that freeze, review it and rebuild staging before installing.** The fifteen full DDL/counter/native fingerprints remain hard requirements: even an unrelated new order or history row invalidates the snapshot. Online inspection and an old backup are candidate evidence, not permission to install against a changing source. Inside the reference transaction, current PRIMARY `FOR SHARE` reads lock and recheck all five parent datasets and reference before-state; they cannot replace the maintenance freeze across the subsequent implicit-commit DDL and atomic rename. Keep maintenance active through independent validation and the strict fresh backup/restore check.

Before preparation, capacity preflight checks the administrator server's actual data-volume filesystem, requiring at least 12 GiB free and at least three times the fifteen tables' reported storage, whichever is greater. This is the whole maintenance budget, including staging and strict reconstruction. Installation first verifies the complete source snapshot, prepared journal, strict stage native/DDL fingerprints and the three exact inner-journal original archives. It then credits only current allocated bytes of those repair-owned fifteen canonical stage tables and three verified old main tables, capped at **2,480,603,136 bytes**. Each must have a distinct exact `Single` InnoDB tablespace; credit uses the smaller of `INNODB_TABLESPACES.ALLOCATED_SIZE` and `FILE_SIZE`. Shared, unknown or repeated tablespaces receive no credit. Unrelated stage objects, estimated `DATA_LENGTH`/`INDEX_LENGTH`, `DATA_FREE` and future copies receive no credit. Required remaining free space is the larger of 9 GiB or the original whole budget minus that capped credit; all other ALTER, redo, backup and operating-reserve allocations remain reserved. A fresh filesystem reading after verification must pass before any source journal or DML is created. The report records actual stage allocation, credit, cap, uncredited tables, required remaining bytes and current available bytes. Test capacity overrides are restricted to isolated random databases with TCP networking disabled and are unavailable through the writing CLI.

A production host with only a few GiB free is refused. The post-install dump and restore still require their own measured capacity checks; credited staging is not permission to delete originals, uploads, binlog or backups. Maintenance duration must come from the full-data rehearsal's measured snapshot/copy/reconstruction/install/verification stages. The small fixture timing is not a production downtime estimate.

The default command is read-only. Writing actions are explicit **bare flags**; `--install=false`, `--prepare=true`, mixed actions, duplicate flags and unknown flags are refused before opening MySQL:

```text
node scripts/repair-reviewed-combined-shadow.mjs --database=EXPLICIT_SOURCE --mysql-admin-socket=EXPLICIT_SOCKET --plan=/absolute/reviewed-combined.json --output=/absolute/preflight.json
node scripts/repair-reviewed-combined-shadow.mjs --database=EXPLICIT_SOURCE --mysql-admin-socket=EXPLICIT_SOCKET --plan=/absolute/reviewed-combined.json --prepare --output=/absolute/prepared-review.json
node scripts/repair-reviewed-combined-shadow.mjs --database=EXPLICIT_SOURCE --mysql-admin-socket=EXPLICIT_SOCKET --plan=/absolute/reviewed-combined.json --install --output=/absolute/installed.json
```

Preparation writes only `_uir_stage_<outer_repair_id>` and its preparation journal. The source installation reuses `_reviewed_unique_index_repairs` and the same database advisory lock as the ordinary tool, distinguished by `mode: combined-shadow`. Native reference changes and their phase commit together. Only afterwards are the three original indexes converted to same-column NONUNIQUE and all three main shadows installed in a single multi-table `RENAME`. Complete originals stay in `_uir_<outer_repair_id>_old_<table>`; only matching reference primary rows are in `_uir_<outer_repair_id>_before_<reference>` and `_after_` tables. No parent table is renamed or rewritten.

```text
node scripts/repair-reviewed-combined-shadow.mjs --database=_uir_stage_OUTER_REPAIR_ID --mysql-admin-socket=EXPLICIT_SOCKET --journal=OUTER_REPAIR_ID --stage --output=/absolute/stage-journal.json
node scripts/repair-reviewed-combined-shadow.mjs --database=EXPLICIT_SOURCE --mysql-admin-socket=EXPLICIT_SOCKET --journal=OUTER_REPAIR_ID --output=/absolute/source-journal.json
node scripts/repair-reviewed-combined-shadow.mjs --database=EXPLICIT_SOURCE --mysql-admin-socket=EXPLICIT_SOCKET --rollback=OUTER_REPAIR_ID --maintenance-confirmed
```

Interrupted stage preparation is inspectable and retains its artifacts; it is not automatically resumed or deleted. Use a separately reviewed fresh repair ID after inspection. Source rollback recognizes reference commit, partial archive-index preparation, forward rename before phase persistence, and reverse rename before reference restoration. It validates all canonical rows, complete original main tables and native reference images before writing. Changed later rows or archives refuse automatic rollback. Matching rollback needs only the source database's journal, complete original target archives and affected reference before/after images; it still works after the independent stage database has been removed. Undo restores the complete original **data** with NONUNIQUE natural keys; it does not make contradictory historical data satisfy UNIQUE, does not authorize resuming normal business writers, and never overwrites unrelated parent changes.

`test/reviewed-combined-shadow-repair-mysql.test.js` uses the shared disposable fixture with the ordinary repair tests. It preserves the sixteen rehearsal behaviors and adds real cross-schema FK refusals and the explicit old-rollback mode refusal. Its source-change injections run after initial installation inspection and before the reference transaction, verifying that current parent reads reject the install without changing any native reference row. This documentation and those fixtures do not assert that production historical data has been repaired or restored.
