# 订单采购覆盖：第二阶段 CPU 优化

日期：2026-10-24（北京时间）。本阶段在 `14bbe8c` 检查点之后单独开发，独立源码审查通过后准备加入首批 release 候选。仅本地代码和隔离测试；未部署、重启服务或操作生产。

## 已确认的成本

第一阶段只读生产对照已经证明，新旧覆盖结果及全部订单状态统计一致。其查询改进不能直接当作整体 HTTP 提速比例：后续测量中供应商后台任务、缓冲和主机负载有明显波动。分段记录显示，纯分配计算本身约有 1.1–2.6 秒，足以占用 Node 主线程。本阶段据此减少重复计算，不改变即时读取或增加长缓存。

## 改动边界

`calculateOrderProcurementCoverage` 内增加本次计算专用的日期 WeakMap、批次身份 Map，以及按产品保存的已入库/待到货批次数组。批次仍按原顺序进入数组，FIFO、人工来源优先、库存盘点、优先级、FBP 保留量、未知采购量和分次收货规则均沿用原算法。索引不写入输入对象，不增加返回字段，不跨请求保留。

这些索引避免历史订单排序反复解析同一时间，以及逐历史订单遍历批次时再次解析时间、检查无关状态；人工来源查找也直接定位原排序中的第一条匹配批次。所有记录仍参与原分配过程，没有截断历史或跳过欠账。

## 验证

- 冻结旧算法作为独立对照。小样本包含日期对象、无效或缺失时间、人工来源、优先级和完整 trace；返回字段、Map 顺序、数组顺序及输入不变均一致。
- 35,000 个合成需求、1,545 个批次并向热门产品偏斜，完整结果逐项一致。日期构造从 9,000,428 次降为 70,104 次。带日期计数的同机 VM 测量为约 5,627ms / 1,995ms；仪表化和合成分布都影响耗时，不能用来承诺线上比例。
- 真实隔离 MySQL 的订单、库存采购业务回归 37/37 通过。只读 profiler 另以同一事务快照对照旧新查询和旧新纯算法，默认企业及独立客户的完整覆盖 SHA、附加库存/批次属性和全部状态统计一致。
- 三个旧 VM 单测文件为 29/36 通过；七条缺少企业 scope 依赖或未返回有效企业的旧夹具失败，在切回冻结旧算法后完全相同。本阶段没有修改旧夹具，也不把整套测试报告为全绿。

证据：`.verification/order-coverage-cpu-regression.log`、`order-coverage-cpu-mysql-regression.log`、`order-coverage-cpu-profiler-comparison.log`、`order-coverage-cpu-v1-unit-baseline.log`。

## 下一次只读核验的工具

`scripts/profile-order-counts-readonly.mjs` 增加 `assembly`：输入查询、需求准备、纯算法、最后整理分别计时，并只记录数组行数。`--compare-algorithm-source=<经审阅的纯算法文件>` 可与 `--compare-coverage-source=<经审阅的覆盖读取文件>` 一起使用，在单一只读一致快照下对照完整结果；比较模式会记录两个算法源码摘要。仅执行经审阅的仓库代码或私有临时副本，不把 VM 当作不可信代码安全沙箱。

本阶段尚未做新的生产性能测试；当前发布完成前不申请追加生产测量。后续需在授权窗口用代表性主机负载复测，分别解释 SQL、CPU 和 HTTP 时延，不能把 SHA 校验及解释计划的耗时混入用户请求时间。
