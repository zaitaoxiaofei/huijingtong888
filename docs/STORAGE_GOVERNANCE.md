# 存储治理与业务兼容性基线

## 目标

在不改变现有业务接口、页面行为和数据可恢复性的前提下，降低 MySQL、大字段、binlog、上传文件和临时任务数据的持续增长。

## 强制安全边界

- 先观测，后止增，最后处理存量。
- 默认审计只能执行只读查询，并必须设置查询超时。
- 未验证读取依赖、备份和回滚前，不删除或清空业务字段。
- 不在生产系统盘余量不足时直接执行大表 `OPTIMIZE TABLE` 或阻塞式重建。
- 所有格式瘦身必须保持现有 API 字段与回退读取能力。
- 原始响应转 OSS 前必须验证对象可读取、校验和一致，并保留 MySQL 引用。
- 清理任务必须分批、可暂停、幂等，并记录删除数量和执行耗时。

## 当前优先级

1. P0：每日表体积、binlog、磁盘水位和异常单行大小报告。
2. P0：统一阻断 Base64 和无边界大 JSON；内容未变化时跳过更新。
3. P1：审计 `listing_category_templates`、`listing_publish_records`、`listing_drafts` 的重复快照。
4. P1：确认 `order_status_history` 是否仍在为未变化订单按小时写入。
5. P1：AI 任务完成后只保留业务摘要，完整过程数据进入可校验冷存储。
6. P2：完成备份与兼容读取演练后，分批迁移存量并在维护窗口回收表空间。

## 基线审计

默认模式只读取 MySQL 元数据，不扫描大表内容：

```powershell
npm run audit:storage
```

仅在维护窗口或确认查询负载可接受时，显式扫描重点大字段：

```powershell
npm run audit:storage:deep
```

查询默认超时 15 秒，可通过 `STORAGE_AUDIT_QUERY_TIMEOUT_MS` 调整，但最大限制为 60 秒。

## 数据分类

| 数据 | 热存储 | 冷存储 | 原则 |
|---|---|---|---|
| 当前业务状态 | MySQL 结构化列 | 可选备份 | 长期保留 |
| 高频查询历史 | MySQL 历史/聚合表 | OSS | 明确保留期 |
| 原始 API 与完整快照 | MySQL 仅存摘要和引用 | OSS 压缩对象 | 内容哈希去重 |
| 图片、视频、PDF | 不进入 MySQL 大字段 | OSS | 禁止 Base64 入库 |
| 任务中间数据 | MySQL 运行状态 | OSS 或自动过期 | 任务结束后瘦身 |
| 临时文件 | 本地临时目录 | 无 | 短期自动清理 |

## 上线门槛

每项存储优化上线前必须证明：

1. 原业务回归测试通过。
2. API 响应字段和状态值未改变。
3. 老数据仍可读取，或存在经过验证的兼容读取路径。
4. 写入失败不会导致核心业务记录丢失。
5. ECS 健康检查通过，并能回滚到上一 release。
6. 变更后持续观察表增长、binlog 和错误率。

## 2026-08-13 基线结论

- `ai_variant_draft_save_items` 约 1194 行、541.5 MB，成功任务仍保留完整队列载荷。
- 成功任务已经生成独立草稿，批次详情接口也不读取 `payload_json`，因此成功后将其收缩为 `{}`；失败任务继续保留原载荷供重试。
- `order_status_history` 约 155 万行，最近每日新增约 4150–18381 行。它同时承担订单轨迹和分析读取，在建立状态变化等价性测试前不改变写入语义。
- 最新 5000 行小样本中，可比较的 3343 行有 3060 行与同订单前一条的状态和分析事实完全一致，重复候选约 91.5%。当前仅建立完整业务指纹，尚未启用跳写；原因是部分历史统计仍按快照行数聚合，必须先消除报表口径依赖。
- `ORDER_HISTORY_DEDUPE_MODE` 使用 `off/shadow/enabled` 三态，默认 `off`。比较失败必须回退到正常写入；生产在完成报表口径验证前不得启用 `enabled`。
- `shadow/enabled` 只有在订单主状态、物流状态、跟踪阶段和同步状态均未变化时才查询最新历史事实；汇总接口返回候选、比较、重复、跳写和比较失败计数，避免为所有同步记录增加额外查询。
- 三张刊登表最新 100 行的大字段平均大小分别约为：模板 134.5 KB、草稿 288.7 KB、发布记录 247.0 KB。现有历史编辑和发布重试仍依赖这些字段，不能直接清空。
- `product_merge_history` 的 4 条历史记录约占 84.8 MB。原实现保存完整产品行，但撤销只消费固定结构化字段；新记录改为撤销字段白名单，保持撤销能力且不复制产品大 JSON。存量快照暂不修改。
- AI 草稿成功队列载荷使用独立的归档工具：默认 dry-run，小批游标读取、gzip 流式压缩、OSS 分片上传并校验远端大小。归档阶段不修改 MySQL；清理必须在归档清单验证后作为独立步骤执行。
- 三张刊登主表仍是最大存量来源；处理存量前必须逐一验证历史编辑、发布回溯和图片权威来源。
