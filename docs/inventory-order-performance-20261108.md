# 库存创建、绑定及订单列表性能

## 基线与边界

- 生产及开发基线为最新发布分支 `release/2026.10.21-task-brand` 的 `b1880bdebb43e89b3de1ca015775085d6ef6a082`（`2026.11.08-inventory-editor-b1880bd`）。用户已更正本轮只合并发布分支，不合并 `main`；性能修改未进入 `main`。
- 生产诊断只使用已有登录权限的有界 GET、服务日志和本机管理员 socket 上的只读元数据查询。创建、绑定、出库及取消回补的写路径在独立、禁用 TCP 的随机测试库内验证。
- 不修改利润公式、库存业务范围、历史扣减及取消回补规则，不以跳过历史订单或提前返回成功来缩短确认耗时。

## 生产观察

- 最近两小时的既有请求日志：`POST /api/products` 约 8.46 秒，`POST /api/online-products/create-product` 约 15.37、17.13 秒，`POST /api/online-products/bind` 约 6.77、13.42 秒。对应路由处理占绝大部分时间，数据库连接取得的最后一次等待约 0–4.4 毫秒。这是历史请求观察，最后一次连接等待不代表整条请求的全部数据库等待。
- 订单 GET 采用北京时间 `2026-08-10` 至 `2026-11-08`、第一页 20 条、关闭统计及物流选项、保留库存可用量。第一条“全部订单”请求在 15 秒上限内未完成，因此停止后续批量采样；不能据此给出延迟分位数，也尚不能区分 SQL、其他路由工作及响应传输的精确占比。
- 后续两个独立有界请求：关闭库存可用量的同页请求也在收到响应头前超过 15 秒；第 12 秒的只读活动查询摘要确认正在处理 `WITH scoped_order_items` 核心订单 SQL（当时状态为 `Opening tables`）。紧接着开启库存量的同页请求约 0.96 秒完成，但核心摘要有 15 秒缓存，不能把这两条请求直接当作库存开关的因果对照。
- 等待备货第一页 20 条约 11.09 秒，其中后端路由约 10.92 秒；等待发运第一页也在响应头前超过 15 秒。未增加并发请求或清空线上缓存。
- `performance_schema` 累计查询摘要说明订单相关聚合曾有大量扫描，但累计值跨越多次版本及不同业务负载，不能当作本轮优化前后的单次对照。

## 改动及验证

1. 出库同步的两个最新历史关联，改为按候选订单查最大观察时间，不再先按全历史表分组；保留相同时间的并列行、空历史、所有原出库及取消回补处理，不改为只同步未完成订单。
2. MySQL UTC 会话初始化按真实物理连接缓存。当前驱动每次借用产生新 Promise 包装，以包装对象缓存会反复执行 `SET time_zone`。新连接及初始化失败仍重新设置，事务和回滚继续使用 UTC。
3. 车型目录普通内置数据按原顺序分为不超过 100 行的批次，原锚点逐条交错顺序不变。种子 INSERT 从 222 条降为 28 条；既有记录 ID、禁用状态、私有企业行、图片、来源和元数据保持。新建种子的自增空洞可能与逐条 INSERT 不同，不重编号既有实体。
4. 订单配方聚合限定为当前页实际配方，保留完整结果字段。大夹具 13,600 个无关共享配方下完整查询约 0.37 秒降到 0.34 秒；线上当前配方表为空，因此此项不能解释本客户 10–15 秒的主要延迟，仍需线上执行计划定位。
5. 实际订单 runtime 边界加入慢请求分段诊断，仅总耗时达到 1 秒时记录固定阶段、耗时及数值/布尔计数；不记录 SQL、订单 ID、企业、名称、请求参数或响应内容。诊断不改响应，时钟或日志失败不影响返回值或原异常。并行阶段及缓存合并等待可重叠，不能将各阶段相加作为总时间；总时间单独计墙钟。

## 执行计划与下一步定位

生产使用一个显式企业范围、只读事务、10 秒语句上限及 12 秒阶段销毁保护，仅读取最近 20 个归属订单的计划。首次旧查询 EXPLAIN 约 5 秒；同连接交替预热后旧/新计划约 153/289 毫秒。因此不能把首次旧计划与后续新计划直接作为提速对照。

计划里多个分组派生表的每键行数估算相乘，出现数百万预计连接行；这不是已确认的实际扫描或业务数量。预热后同快照执行两版真实核心 SELECT 约 217/200 毫秒，均 20 行且全部字段哈希一致。这个最新 20 条样本的核心读取明显快于完整路由，尚需检查筛选、补充信息、库存余额及实际连接/并发等待，不能声称已修好整页的 10–15 秒问题。

以上执行计划及诊断接线结果为上一阶段记录：当时真实 facade 对照的 45 条 SQL 文本和参数逐条相同，完整响应哈希相同；库存优化和分段日志随后已随 `1f58ef7` 发布。本轮后续改动的后端聚焦回归分别为 9/9、20/20 通过，前端聚焦回归 15/15 通过，另有两项真实 Chrome 夹具通过。这些是对应范围的验证，不表示仓库全部测试均通过。生产参数、响应正文、客户字段、凭据及原始 SQL 参数不写入本文或验证报告；部署后的生产验收由发布记录另补。

## 订单首屏与后台让路验证

前批库存创建、绑定优化及慢请求分段诊断已随 `1f58ef7` 发布。后续一次生产订单请求总计约 32.43 秒，其中 `core_sql` 包装段约 31.05 秒。该段包含取连接、读取让路和驱动执行，不能直接当成纯数据库执行时间；其他并行阶段也不能相加解释总耗时。

本次追加改动仅调整首屏依赖和读取优先级。普通查询、筛选、翻页及强制刷新均先请求不附带库存可用量的订单行，再沿用当前页批量库存接口异步补齐实物／可用数量。订单先绘制，库存事实随后回填；未取得的事实不补为零，真实零值正常保留。采购覆盖、状态筛选、分页总数及行顺序仍由既有订单响应负责。库存请求继续核验企业、请求版本和当前行，翻页、保存后重读、切换企业或离开页面时，旧回包不能覆盖新页面。

生产仅作有界、只读、顺序采样，每页 20 条、保留相同的北京时间范围，得到以下观察：

| 队列 | 行请求附带库存事实 | 行请求延后加载库存事实 |
| --- | ---: | ---: |
| 等待备货 | 约 12.8 秒 | 约 1.26 秒 |
| 等待发运 | 约 6.8 秒 | 约 2.26 秒 |

两组请求不是同一时刻的随机交叉实验，缓存、预热、执行顺序和后台负载均可能影响结果。这些数字说明首屏可以先完成，不能用来承诺固定提速倍数，也不能据此认定库存计算本身是所有长尾延迟的根因。另一次精确核对确认，当时真实备货页的 20 个订单与最新全部订单样本集合相同；因此不再用“未覆盖复杂备货订单”解释该批 SQL 原型没有改善的结果，但此集合相同也不代表所有日期和页码永远相同。

后端只在核心 SQL 的前台 `mysqlQuery` 调用期间启用交互读取保护，返回或异常后立即释放；背景调用不会为自己建立该保护。独立库存余额、共享背景刷新 Promise 和完整补充信息流程均不包在保护范围内，避免前台等待的余额刷新反过来等待同一保护。它只暂缓尚未开始的背景读取，不中断已运行的扫描，并保留原有有界等待，不能视为数据库互斥锁或长尾根因修复。真实 MySQL 回归验证了核心结束后余额立即继续、异常释放及背景调用不自等；前端回归覆盖首屏先显示、零值、失败重试、缓存行补齐、翻页和企业隔离。

追加诊断观测到触发器相关内存占用和表缓存开表／miss／overflow 压力，但尚未证明其与偶发长延迟的因果关系。独立环境将表缓存从 2000 对照到 4000，可消除该样本的热查询开表周转，耗时仅约 326→315 毫秒，不能据此推断生产 31 秒问题会被全局扩容解决。会话 profile 的尾部 100 个阶段仅覆盖约 0.115／1.213 秒；缺少早期 Opening tables 记录也不是排除开表耗时的证据。该保留上限可见 [MySQL 8.0.46 源码](https://raw.githubusercontent.com/mysql/mysql-server/mysql-8.0.46/sql/sql_profile.cc)，资源计数也有[官方说明的进程口径限制](https://dev.mysql.com/doc/refman/8.0/en/show-profile.html)。

scope-first、direct scopes、product-scope 和 prepared/text 协议对照均保留在验证目录。已测结果哈希一致，但尚无稳定的生产端到端收益；其中 product-scope 候选先执行约 1.77 秒、原查询随后约 0.19 秒，预编译的 prepare 本身约 447 毫秒，不能只用后续热执行的较短时间作上线依据。本轮不将这些 SQL／协议候选并入业务源，不修改生产全局 MySQL 配置，最终采用的后续措施仅为首屏延后补齐库存事实和核心前台读取让路。
