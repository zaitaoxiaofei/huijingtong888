# 订单加载与采购保存性能修复

## 定位结果

- ECS 日志中待采购列表耗时约 68 秒，分栏统计耗时约 69 秒。
- 只读拆分测量：需求查询 65.4 秒，其余库存、采购、入库查询均低于 0.6 秒。
- `EXPLAIN ANALYZE` 显示运输历史的最早状态时间查询执行 26,767 次，单次平均约 1.75 毫秒。原索引不能覆盖 `last_status_changed_at`。

## 修改

- 新增 `(order_id, status, last_status_changed_at)` 覆盖索引；不改变需求计算或库存分配规则。
- 当前页和分栏数量分开请求，普通列表不再等待全量采购核算；修改后取消旧统计请求并清除统计缓存。
- 订单行的库存拣货、质检、计费物流等独立查询并行执行，行顺序不变。
- 采购保存成功后独立刷新列表，刷新失败不再误报采购保存失败。
- 移除保存路径中查询后从未参与计算的全局预留汇总；已填写价格异常理由时跳过重复历史均价查询，成本记录仍然写入。

## 验证

- 相关回归测试：46 项通过，1 项独立 MySQL 集成测试未启用。
- 编码检查、SQL 绑定检查、前端构建通过。
- 使用会话临时历史表模拟覆盖索引，没有修改生产业务记录或永久索引。
- 500 条较早订单样本：原查询 783 毫秒，覆盖索引样本 232 毫秒，523 条需求结果逐字段一致。
- 500 条较新订单样本：原查询 267 毫秒，覆盖索引样本 185 毫秒，644 条需求结果逐字段一致。
- 样本耗时不代表全量接口或浏览器端到端耗时；部署后需重新测量冷缓存列表和采购保存。

## 发布要求

合并到干净的主分支/发布分支后使用 ECS 发布流程，**不要跳过数据库初始化**。初始化脚本包含在线创建索引的幂等迁移；新索引未创建时，数据库侧性能修复尚未生效。

可在已加载数据库环境的发布目录运行 `node scripts/profile-order-coverage.mjs`，重新执行样本对照。脚本仅写会话临时表，连接关闭后自动释放，不执行生产采购操作。
