# Unified Ozon browser plugin

Implementation version: collector plugin 1.5.1, pending fresh ECS rollout approval and production package acceptance. Unified 1.5.0 was released and accepted on 2026-11-05; this follow-up addresses browser-worker registration and its diagnostics.

## One installation and one connection input

`ozon-erp-collector-plugin` is the unified installation. Its main popup provides product collection and shop analytics tabs. The only editable connection field is the enterprise plugin key. The service URL is fixed to `https://erp.hjt888.xyz`; the existing authenticated `GET /api/local-plugin/plugin/status` supplies the enterprise selector from the verified token principal. A read-only production check confirmed this endpoint accepts the enterprise token alone, without a separate site-access token or cookie.

The canonical key remains `ozon-erp-local-plugin-token`. Existing product-extension settings can be reused when updating the same extension installation. A separate extension's private Chrome storage cannot be silently imported; an operator coming from the standalone analytics extension pastes the enterprise key once. Do not introduce a new manifest key or promise extension ID preservation when loading an unpacked package from a different folder.

Local saving is independent of remote validation. Failed validation does not leave the popup at saving, expose the key, or authorize a different enterprise. Concurrent saves preserve the latest accepted intent even when hashing or storage completes out of order. Connection metadata is bound to a key fingerprint. A key associated with another historical ERP origin requires explicit re-entry; content and background paths cannot forward it to a different service. Explicitly empty canonical keys never fall back to a separate analytics key.

The popup always shows the installed manifest version and the latest server version. Optional updates are visible without turning them into mandatory updates. This addresses the old product popup's `update_required`-only rendering, which hid normal available updates.

## Runtime and session ownership

The standalone `pivot-table-master` source remains compatible. `scripts/sync-unified-analytics.mjs` generates an IIFE-wrapped analytics runtime and copied assets under the unified plugin's `analytics/` directory. Do not concatenate both original backgrounds into global scope: they share top-level declarations. Keep MAIN-world document-start relay/analytics ordering, isolated relay messaging, and existing frame behavior. Do not inject into about:blank relay parser frames.

Both runtimes use `unified-config.js` for the same service, enterprise and key. `unified-runtime.js` coordinates Seller navigation with product requests. Analytics preparation waits for active product work, blocks new product claims, and retains its gate until the underlying preparation actually completes. Legacy Seller bridge requests also participate. A timeout while waiting must not release a gate around navigation that is still executing. The unified analytics adapter bounds remote fetch/body waits so a stalled binding probe cannot monopolize the shared preparation gate.

The unified ERP bridge advertises collector and sellerAnalytics capabilities and its actual extension instance ID. App and analytics-page handshakes prefer that live instance, correlate store-check results by instance, and discard late responses after a switch. Tenant and live-company guards remain authoritative. After switching to the unified package, disable the separate old analytics extension and refresh ERP/Seller pages; old installed code cannot be changed by the new extension.

## Distribution and compatibility

`capabilities.json` is the explicit server distribution boundary. When both capabilities are true, the existing `plugin` and `analytics_plugin` update fields advertise one version and the same `ozon-baodan-erp-plugin-1.5.1.zip`. Unversioned legacy download aliases resolve to the canonical unified archive. Explicit old versioned analytics archives retain their actual old manifest version. Existing minimum-version/system-bug policies remain explicit; merging features does not force every old installation to update.

`npm run package:plugin` first regenerates analytics assets, then creates one versioned ZIP and byte-identical aliases. `COLLECTOR_PLUGIN_OUTPUT_DIR` can isolate local packages. Windows uses native tar with explicit top-level entries, so `manifest.json` is a root archive entry. The normal deployment packager always rebuilds the collector ZIP and selects versioned packages by source manifests, instead of reusing stale aliases or selecting an unrelated higher-version file from a sibling task. Verify all package files against source and keep the sibling source mirror at the same manifest version. A release still requires the normal remote-release merge, fresh ECS approval, and verification of production metadata and downloaded archive contents.

Local tests cover one-key save/validation, stale and concurrent saves, both real background scripts loading together, task/navigation coordination, instance selection, store checks, update compatibility, download aliases, and the existing HTTP coordinator on local 8788. Chrome/Ozon/tenant fixtures are synthetic except for the explicitly noted read-only production identity endpoint check. Popup visual verification uses a separate headless test session, not the operator's logged-in browser.

## Browser-worker registration repair (1.5.1)

Read-only production evidence at 2026-11-05 23:59:58 Beijing time showed a recently reporting 1.5.0 instance with a Seller tab and live page company, but no Chrome-cookie company and `identity_missing`. The default-enterprise coordinator had no live workers, and Nginx showed no heartbeat/claim/result calls in the inspected interval. These observations identify a pre-registration failure, not a successful multi-shop run. They do not establish that every enterprise has no workers or that partitioned cookies caused this particular client failure.

Chrome's [cookies API](https://developer.chrome.com/docs/extensions/reference/api/cookies) reads unpartitioned cookies by default. Chrome 132+ provides `getPartitionKey({tabId, frameId: 0})`, returning `{partitionKey: ...}`. The [Chromium API definition](https://github.com/chromium/chromium/blob/main/extensions/common/api/cookies.json) and [filter implementation](https://github.com/chromium/chromium/blob/main/extensions/browser/api/cookies/cookies_helpers.cc) also confirm that an empty partition filter can select every partition. Never query with an empty key to recover an identity.

The shared `seller-cookie-context.js` reader resolves the actual tab's cookie store, then reads unpartitioned cookies and the API-returned top-frame partition within that same store. It never guesses a partition or substitutes an ERP-expected company for cookie identity. Missing cookies remain unknown, conflicting companies fail closed, and the live page company must still match. Older Chrome without `getPartitionKey` retains the unpartitioned path. The unified analytics adapter uses the same reader; the standalone analytics source remains unchanged.

Configuration changes, completed Seller navigation and company-cookie changes wake registration immediately. A definite no-worker response forces a fresh scan and heartbeat before one retry using the latest connection context; uncertain accepted batches retain the existing no-replay behavior. Authentication/rate-limit cooldowns remain enforced.

A subsequent operator screenshot showed `SELLER_NAVIGATION_FAILED stage=warm_analytics` with Chrome's `Navigation rejected.` error. The generated runtime reproduced this exact failure when the first `tabs.update` resolved before commit, retaining the old URL and a target `pendingUrl`; warmup immediately issued the same navigation again. The unified adapter waits for the existing target navigation, requires its actual committed URL and complete status with no pending navigation, and blocks further steps on timeout. It does not retry a real navigation refusal, create a replacement tab, or weaken identity validation. Chromium's [TabsUpdateFunction implementation](https://github.com/chromium/chromium/blob/main/chrome/browser/extensions/api/tabs/tabs_api.cc) emits that generic error for multiple content-layer rejection causes, so the screenshot alone does not establish why this particular browser rejected navigation.

The popup exposes a local, read-only snapshot and an immediate reconnect action. Registered local companies and the server's last reported available-company count are separate values; neither proves concurrent dispatch. Diagnostics contain controlled codes and text, counts and tab IDs, never credentials, cookies or raw URLs. The product card labels `browser_pool` as ECS scheduling, since the actual Ozon request still runs in a verified browser session. Acceptance of real multi-shop operation requires an uncached batch completed by at least two distinct authorized source companies after installation.

Operator-facing labels use “云端采集池” and “云端调度”, following the user's preference for plain service terminology. Technical deployment targets remain ECS.

Saved shop/auth bindings are persistent records, separate from the browser pool's short-lived heartbeats. The current analytics synchronization UI queues plugin work and automatically checks live identity; it does not enable the separate server-direct start route merely because a binding exists. A verified, already-open analysis page takes the browser fast path without forced navigation or rebinding. Operators should not manually repeat recognition for every synchronization. An unexpired saved cookie is insufficient proof of server-direct authorization: prior live probes were rejected while browser-session access worked. Only expired/revoked sessions, missing pages or conflicting shop identities require recovery.

Local acceptance on 2026-11-06: 241 focused tests passed, including the actual generated navigation runtime and a real HTTP coordinator on local 8788 fed by actual worker/helper factories for two synthetic shops (one partition-only). The same uncached batch completed with both source companies, no fallback, and tenant isolation. These are controlled browser/Ozon fixtures, not live Ozon success measurements. The normal plugin packager produced 33 files; every archived file and the sibling source mirror matched the packaging source byte for byte. Both local update domains selected 1.5.1 and its exact versioned ZIP. Encoding and syntax checks passed. An already failing source-regex test at the release baseline was updated to require the current targeted plugin-instance ID on cancellation and wake; no ERP frontend file was changed. ECS deployment, downloaded-production-package checks and the operator's actual session acceptance remain pending.

## SKU daily collection and browser identity

Unified plugin 1.5.6 uses a persistent installation UUID in addition to Chrome's extension ID. Content-page checks, status heartbeats, preparation requests and result attribution use the same browser identifier across worker restarts. Chrome's shared extension ID alone is not a computer identifier. Older plugins keep selected-shop collection support; the new discovery and device attribution capabilities are optional. Refresh ERP pages after updating the extension so its new content bridge can announce.

The SKU monitor keeps all-shop inventory comparisons separate from collection: collection is scoped to one locally verified Seller shop, and the server revalidates that instance against the owned shop. Switching the ERP filter does not switch the Seller account. Daily status distinguishes unclaimed queues, active requests, finished requests awaiting publication and published daily records. Complete days are skipped by default, including scheduled dispatch. Cross-browser completion is named only when a recorded collector identifier supports it; historical records with unknown origin remain labelled as stored data.

Compact facts are retained for 30 complete Beijing report dates, while original pages and completed temporary runs retain their one-day cleanup policy. Widening retention cannot reconstruct already deleted facts: missing older dates must be collected again from the currently logged-in Seller session. Status polling reads metadata and SQL counters without downloading all SKU histories.
