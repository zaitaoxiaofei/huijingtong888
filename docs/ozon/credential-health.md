# 店铺密钥到期与同步健康检查

第一阶段，2026-11-04。开发基准：`c26d366e83b77c6a56bc3fcfc0fb9b670473f568`。

## 操作行为

- 企业店铺页显示当前店铺的授权状态、官方到期日期、剩余天数和检查记录；时间统一为北京时间。
- 每日后台任务 `ozon_credential_health` 遍历有效订阅企业的启用店铺，首次启动延迟一分钟；新增店铺或替换密钥后立即检查。管理员也可手动检查，同一密钥一分钟内不重复探测。
- 通过 `POST /v1/roles` 只读检查官方 `expires_at` 与角色/方法列表。授权查询通过不代表所有业务接口都有权限，也不代表旧数据已补齐。缺失或无效的到期时间不按创建日期推算。
- 提前 30、14、7、3、1 天分阶段通知；7 天内每日提醒。过期、撤销、缺失、权限不足、未接受卖家协议、临时检查失败分别提示。通知保存在已有站内通知中心，收件人为当前企业的负责人、管理员和绑定店长，账号和成员关系须有效。旧默认企业自动分配的 owner 不自动获得管理权限。
- 告警去重包含企业、店铺、密钥指纹、阶段、日期和收件人。已读不是恢复；禁止手动把密钥告警设成已处理。后续验证通过后解除对应旧告警，到期预警按当前阶段保留。
- 广告授权独立，不将 Seller API Key 的检查结果当成广告凭据正常。

## 数据状态

记录订单、商品与详情价格、库存（含 FBP 库存工作台）和官方原始账单的本次尝试、最后成功时间以及查询范围。只有完整成功才更新最后成功时间。指定商品、日期或状态的成功不能表示所有历史数据完整。

历史时间不回填猜测值，首次记录前显示未知。换钥后的授权恢复不清除同步失败状态；各模块仍需通过已有定时任务或现有手动同步入口补拉并核查。此版本不新增历史回填任务，不修改既有利润公式，也不自动重算冻结利润。

库存 API 报错时不再从在线商品缓存重新写入库存快照，否则旧值会获得新的同步时间。空且不可确认的库存响应也不清空已有快照。库存持久化中途报错仍报告未完整完成，应检查后重试；本阶段不重构旧批量库存写入事务。

## 存储与并发

使用已有 `system_settings` 的 `ozon.health:<tenant_id>:<shop_id>` 记录，不新增表或数据库迁移。键值只保存指纹和健康元数据，不保存密钥、Cookie 或原始供应商错误文本。业务数据写入成功但元数据保存失败，不把已提交业务写入伪装成失败并诱发重复写；记录服务端诊断日志供排查。

检查开始和结果分别在短事务中锁定当前店铺及元数据，外部网络请求不持有数据库事务。结果写入前重新验证企业订阅、店铺启用状态、当前密钥指纹和检查编号，拒绝旧密钥或较早检查的在途结果。通知与状态在同一事务写入，提交后只广播当前企业收件人的刷新事件。读取接口只投影公开元数据。

接口：`GET /api/shops/ozon-health`、`POST /api/shops/ozon-health`（`shop_id`）。仅当前企业负责人、管理员，执行时重新验证成员身份；客户端不能指定企业归属。

- 52 项聚焦单元/路由测试通过，覆盖提醒阈值、不同错误分类、缺失到期时间、换钥竞争、旧结果覆盖、同步失败保留历史成功时间、店铺权限及旧缓存不再写入。

- 前端生产构建、SQL 参数绑定检查、接口文档一致性、UTF-8 检查通过。浏览器在本地 8788 使用虚构店铺验证到期/过期状态、同步失败详情及编辑入口，没有访问真实店铺密钥。

## 发布计划与限制

本阶段尚未部署 ECS，未重启生产、未修改生产配置。当前站内通知功能只在发布后开始运行；没有新增短信、邮件或企业微信通知。

获得具体部署批准后，先复核远程发布 head 和已部署 hotfix 的归并情况，再合并任务分支并从确切合并提交构建可复现产物。发布后只读检查任务注册、健康记录与脱敏通知；新的数据成功时间须由各模块真实同步产生。回滚应用代码不会删除业务数据；已生成的元数据与站内通知可保留审计，不批量清除。

后续顺序：仓库同步 → 官方财务账单源与订单费用核对 → 促销报名 → 广告调价。11 月 23 日前做 `total_items` 兼容回归；多选面单另做耗时定位。FBO 供货单与评价同步不在本轮业务范围。
