## 利润计算器哪些可以复用

`src/services/pricing-reference-rate.js` 使用俄罗斯央行官方 XML 接口，`Value / Nominal` 得到 **1 CNY = N RUB**，当前解析到四位小数。RUB 折 CNY 应除以该值，不能把方向用反。

计算器打开页面时请求 `/api/tools/pricing/reference-rate`；该模块按请求抓取、8 秒超时，进程内缓存 1 小时。没有每日定时写表、持久归档或备用源。获取失败时计算器提示手填，没有把最新抓取值写回系统汇率表。

历史函数已有 `date_req=DD/MM/YYYY` 查询能力：把订单时间转北京日后请求指定日期，结果保存在无期限的内存 Map，重启会丢失，主备进程各自缓存。可以复用取价/解析能力，不能直接把计算器的利润公式搬到订单：计算器本身是人民币售价减人民币成本，汇率还用于卢布佣金档位与物流折算。

官方接口文档确认指定日期和省略日期的请求方式；省略日期返回最近登记日期：[CBR XML 文档](https://www.cbr.ru/development/sxml/)。央行页面明确这些是官方参考汇率，并不承诺按该报价买卖外汇：[CBR 每日参考汇率](https://www.cbr.ru/eng/currency_base/daily/)。因此不应将其称为银行实时成交价。

## 合理性分析：用户要看的应是纯汇率影响

按下单日记录预估、按签收日定经营核算汇率，是合理且可复核的管理口径。与此同时，**实际利润减预估利润不是纯汇差**：还混有原币佣金、物流、采购成本、退款及金额确认的变化。

建议分开记录：

1. **下单预估利润**：下单日汇率与当时已知的费用、成本；保留基线，后续成本修订不抹掉初始预估。
2. **签收口径利润**：以真实签收北京日冻结汇率，按已知业务事实计算。账单未齐时明确待确认；真实费用补齐后仍用冻结的签收日汇率完成核算。
3. **其中：纯汇差**：同一份原币实际净额、同一份人民币成本，只替换下单和签收两天汇率。其余费用变化单列。
4. **后续结算差额**：如需反映实际换汇到账金额，另记录银行/支付渠道实际汇率与手续费，不能拿央行参考值假称已实现的现金汇兑结果。

对于方向 `R = RUB / CNY`，以实际原币净额作为归因基准：

```text
纯汇差 = 实际净卢布金额 × (1 / 签收日汇率 - 1 / 下单日汇率)
其他业务差额 = 实际业务按下单汇率计算的利润 - 下单初始预估利润
签收口径实际利润 - 初始预估利润 = 纯汇差 + 其他业务差额
```

这里的“净卢布金额”是已核实以卢布计量的收入减卢布费用；不是订单整笔人民币利润，也不是简单取商品标价。人民币收入/采购/包材等不重复换汇；其他币种应各按自己的币种及日率换算后再汇总。页面显示 CNY 不能证明原始结算币种，当前财务样本空币种必须先核实。

假设示例（非当前真实汇率）：扣除卢布费用后的收入固定为 1,000 RUB，人民币成本 50 元。

| 项目 | 下单 | 签收 |
| --- | ---: | ---: |
| 汇率，RUB/CNY | 10 | 12.5 |
| 同一原币净额折 CNY | 100 | 80 |
| 人民币成本 | 50 | 50 |
| 利润 | 50 | 30 |

其中纯汇差为 **-20 元**。若采购或运费也发生变化，这部分另列，不能都归咎汇率。

## 后续方案边界，尚未实现

- 每日汇率持久归档，保留币种方向、来源、请求业务日期、来源生效日期、抓取时间、精度及版本。同一来源修正不能覆盖订单已引用的快照；公共参考数据可平台共享，订单和企业利润快照严格归属企业。
- “实时更新”在本需求中建议解释为自动获取最新有效的每日参考值；历史核算按日锁定，不让过去订单跟着当前页面刷新漂移。不能用可能已发布的未来生效记录覆盖今日。
- 请求北京日与央行返回生效日分别保存；休市/无新报价沿用有证据的有效参考值，并标明其生效日。请求失败、历史日期无证据或签收日缺失应标待补，不悄悄用今天或 11.32 代替。
- 用真实 `ordered_at` 和真实 `delivered_at`，不是 ERP 首次同步到该状态的时间。部分签收、退货、重发、签收时间纠正的业务边界须明确。
- 换汇只改变需要折算的金额，不能顺带重新选择下单时已确定的物流计价版本、佣金档位或修改人民币采购成本。
- 下单初始预估、后续预估修订与签收/账单实际结果分别保留。费用后补可产生修订，但不能改签收汇率基线或把总差额全标成汇差。
- 明确逐费用、逐明细或汇总后的舍入层级；分位尾差独立核对，不能计入纯汇差。
- 已发布 V1 冻结。实施时采用新业务规则版本和明确切换，沿用同事务修订保护；旧订单不随日常汇率刷新自动重算。历史补算先单独预览受影响范围和金额差，再确定处理范围。

## 待与用户确认的业务口径

1. 是否采用“签收日冻结核算汇率，账单补齐后按该汇率确认利润；真实到账的结算差另记”这一建议。它符合用户关注下单到签收期间汇率波动的目标，也保留财务费用尚未齐全的事实。
2. 纯汇差建议按同一实际原币净额对比两日汇率；这样可以与成本、佣金等业务差额严格对上。需要原币收入与原币费用的可靠来源，不根据当前页面标签推断。
3. 历史订单是否按新口径另做影响预览，以及无可靠币种、签收日或历史汇率证据的订单如何标记。当前没有获得批量改写历史利润的执行范围。
