# 订单筛选与首屏库存补充

## 页面交互

订单顶部移除“有争议”和“待补采购记录”标签。旧的标签排序偏好会过滤这两项；旧页面状态恢复到已移除标签时回到等待备货。历史订单及采购记录保留原数据和原入口。

“即将超时”和“采购在途超时”放入顶部状态筛选区。点击打开天数弹层，未启用时默认 3 天；调整下拉值只修改草稿，确认后才查询，取消、点外侧均丢弃草稿。两项可以组合并分别取消。普通“采购在途”状态仍然独立存在。

原有筛选含义与排序不变：即将超时包含已经超时的订单，0 天表示已经超时；在途天数范围 1–10，10 表示 10 天及以上。

## 首屏库存

普通订单首屏曾经只读取进程中已经存在的完整采购覆盖缓存；冷缓存没有库存数值。后续统计请求只更新标签计数，没有刷新行数据，因此“可用／实物”可能长期停留在待核对。

列表返回后立即发一个当前页订单 ID 批次请求，使用独立的 `inventory_availability` 补充产品实物和可用数量。完整采购覆盖继续负责订单分配、在途分配和采购缺口。切换页码或筛选会取消旧请求，并用请求序号阻止过时响应覆盖当前列表。未知和失败不补零；负实物显示待核对。

契约与租户隔离见 [order-inventory-availability.md](order-inventory-availability.md)。所有当前页产品的需求仍统计其整个租户范围，而非只扣当前页需求。

## OGL 筛选

只选择物流商、未选择具体物流方式或官方渠道、且 `includeLogisticsOptions=0` 的请求走轻查询。OGL 先在物流白名单字段中做宽松候选筛选，再把候选原始数据交给现有 `classifyOrderLogistics` 最终判断。SQL 同时检查 flat 和 wrapped 字段只为避免遗漏，最终识别仍严格遵守原始数据层优先级和单词边界。客户名、商品名、URL 和计费规则不参与 OGL 候选。

其余物流商轻查询保留原始识别数据，跳过计费关联和旧物流规则匹配。选中具体渠道、旧物流方式，或主动请求物流选项时，继续使用完整查询及原有计费渠道回退。

轻查询缓存只保存订单 ID 和已识别物流商，缓存键包含租户、物流商、店铺和日期。`includeLogisticsOptions=0` 时三类物流选项均返回空数组；前端保留固定物流商选项，主动展开渠道时另外取完整选项。

## 验证记录

2026-10-21 ECS 同一只读快照测量，范围为北京时间 2026-07-23 至 2026-10-21：

- 首屏 20 单、15 个实际库存产品：余额聚合约 392 ms，完整产品范围采购覆盖约 4849 ms；实物与可用逐产品一致。
- 新订单授权与产品派生 SQL：20 单、15 个产品约 111 ms；跨企业请求在读取余额前被拒绝。
- 原物流汇总读取约 1.75 万单、77 MB 原始数据。旧版本完整服务首次 OGL 查询约 13909 ms，再次查询约 76 ms。
- OGL 宽松候选 SELECT 约 1667 ms，返回 2 单、约 9.8 KB；现有识别器终判的订单 ID 与全量识别完全一致。
- 多次逐字段 JSON 投影、JSON_TABLE 和物化投影经过测量，均未采用。

以上 SQL 和服务测量不代表浏览器端到端耗时。此次没有修改计费规则选择、利润公式、历史利润、库存流水或采购分配算法。
