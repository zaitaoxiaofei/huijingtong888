# 平台身份与企业成员迁移

`people` 保留全局登录身份、密码和历史业务引用。平台权限只来自 `platform_grants` 中启用的 `super_admin` 授权；姓名、旧 `people.role = admin`、企业负责人或业务岗位均不能产生平台权限。

企业负责人/管理员/成员保存在 `tenant_members.role`，业务岗位保存在同一成员关系的 `business_roles_json`。同一人员可以有不同企业岗位，也可以同时具有平台授权和明确的企业成员关系。仅平台账号不需要默认企业成员关系。启动过程不自动新增平台授权或默认企业成员。

## 默认企业旧账号兼容

旧版启动曾把所有启用人员自动加入默认企业并标为 `owner`。这些历史记录不能直接代表真实负责人权限：当默认企业成员的 `business_roles_json` 仍为空，且其原有效岗位不含 `admin` 时，会话、企业成员列表和操作权限按普通成员处理，保留原有业务岗位。原 `roles_json` 覆盖旧单角色的规则不变。旧全局管理员保留企业业务管理身份，但仍需明确的平台授权才能管理平台设置。

该保护只计算有效权限，不在启动时修改人员、密码或成员记录。已明确填写成员业务岗位的新建、审核迁移或平台成员授权记录，以及其他企业明确设置的负责人身份，不受此历史兼容保护降级。企业人员修改姓名或密码时会沿用有效成员身份，不会把历史自动负责人悄悄转成正式负责人。最后负责人检查同样只计算有效负责人。

只读迁移盘点中的 `stored_role` 是数据库历史值，`role` 是当前有效身份，便于在正式迁移前核对。默认企业仍有有效成员关系的人员可以沿用原密码登录；没有有效企业关系且没有有效平台授权的账号会被拒绝。身份迁移撤销变化账号的旧会话，要求重新登录，不会重置密码。正式发布前仍需核对实际人员名单、企业角色及明确的平台授权，不能仅凭代码回归保证生产所有账号不受影响。

## 企业人员管理边界

- 企业人员接口只接受当前会话企业，由数据库重新检查操作者的启用成员关系及负责人/管理员身份。全局旧管理员岗位及平台身份不能替代本企业管理身份。
- 列表包含停用成员，返回 `member_active` 和 `account_active` 两个不同状态，不返回密码、微信绑定凭据或平台密钥。
- 创建账号及加入当前企业在同一事务中完成。新账号的企业岗位只写入成员关系，不允许企业管理员通过人员 ID 关联任意已有全局账号。
- 修改企业角色、业务岗位或成员启用状态只影响本企业，并撤销该企业的旧会话。不能停用全局登录身份，不能删除其他企业关系或历史业务引用。
- 已存在其他企业成员关系或明确的平台授权记录时，身份字段返回 `can_edit_identity: false`，包括其他关系暂时停用的情况。仅当前企业独占且无平台授权的账号，才允许企业管理员修改姓名、登录名、头像及重设密码；更改后撤销该账号旧会话。
- 必须保留最后一位启用的企业负责人。额度按最终成员状态检查，排除一位主负责人，其余启用成员占子账号额度。

## 只读盘点

在项目目录运行：

```text
node scripts/migrate-platform-enterprise-identities.mjs
node scripts/migrate-platform-enterprise-identities.mjs --manifest=/absolute/path/reviewed-identities.json
```

默认只执行 `SELECT` / `SHOW`，不会创建表、补成员、写授权或撤销会话。输出只有人员 ID、岗位和企业 ID，不包含密码及凭据。旧管理员会显示为历史业务岗位，不会被自动认定为平台超级管理员。

## 明确审查的迁移清单

下方 ID 仅为结构示例，不代表实际人员。应用前必须逐个核对实际人员 ID 和企业 ID。每个列出的人员都必须明确设置 `platform_role`，并完整列出其迁移后要保留的企业关系；未列出的旧企业关系会被停用而不会删除。未列入 `accounts` 的人员不作变更。

已归档企业中现有的停用成员关系可以在清单中以 `active: 0` 保留，不会被重新启用；不能向已归档企业新增成员或恢复停用成员。

```json
{
  "version": 1,
  "reviewed_by_person_id": 101,
  "reason": "核对人员与企业归属后拆分平台和企业权限",
  "accounts": [
    {
      "person_id": 101,
      "platform_role": "super_admin",
      "memberships": [
        { "tenant_id": 1, "role": "owner", "active": 1, "business_roles": ["operations"] }
      ]
    },
    {
      "person_id": 102,
      "platform_role": "super_admin",
      "memberships": []
    },
    {
      "person_id": 103,
      "platform_role": null,
      "memberships": [
        { "tenant_id": 1, "role": "member", "active": 1, "business_roles": ["packing"] }
      ]
    }
  ]
}
```

三种记录分别表示双身份人员、仅平台账号、仅企业员工。开发账号只有经过明确审查的 `super_admin` 授权，没有按名称自动判断的“开发者”权限。新企业岗位界面不提供旧 `admin` / `technical` 选项；迁移仍接受这些旧岗位值用于兼容，其本身不产生平台权限。

## 显式应用

生产环境须使用已检查的 ECS 发布流程。安排迁移时先保存数据库备份、只读检查清单，停止旧版本服务，使用新代码执行迁移，再启动并验收新版本。旧启动逻辑不能在迁移后继续运行，否则可能重新补入默认企业成员。

```text
node scripts/migrate-platform-enterprise-identities.mjs --apply --manifest=/absolute/path/reviewed-identities.json --mysql-admin-socket=/var/run/mysqld/mysqld.sock
```

管理员连接只接受明确指定的本机 Unix socket 或 Windows 命名管道，不使用应用账号隐式升权。应用模式先准备授权表、成员岗位列和迁移日志表，再在同一事务中重新检查人员、最终平台管理员、企业负责人和额度，写入审计快照并撤销权限发生变化账号的旧会话。失败时回滚身份和成员变更；准备阶段创建的空表或新增列可能保留。

应用后检查：平台专用账号可以独立登录且没有企业业务上下文；普通员工不能访问平台设置；双身份账号拥有明确授权和正确的企业成员关系；企业 A 管理员无法修改企业 B 成员、全局角色或平台授权。重复运行同一清单不会再次撤销未发生权限变化的账号会话，但仍保留操作审计。

## 隔离 MySQL 验证

`test/platform-enterprise-identity-mysql.test.js` 使用 `TENANT_TEST_MYSQL_SOCKET` 指定的隔离实例，并且只创建、使用和删除随机命名的 `ozon_identity_test_*` 测试库。测试直接执行真实 MySQL SQL，覆盖平台专用及双身份会话、企业成员事务、并发额度、最后负责人、共享身份及授权记录的锁定检查、迁移审计失败回滚。测试不会读取应用配置，也不会连接应用业务库。

```powershell
$env:TENANT_TEST_MYSQL_SOCKET = '\\.\pipe\OzonSaasLaunchTest'
node --test test/platform-enterprise-identity-mysql.test.js
```

上述命名管道由开发环境单独提供；没有指定测试实例时，测试会跳过。本批次在隔离测试库验证了 20 个场景，包含默认企业历史自动负责人兼容及其编辑、迁移保护。本文档及迁移脚本不表示已对业务数据库执行迁移或完成部署。
