# 订单翻页诊断与打印模式交互调整

## 基线与范围

- 基于远端 `release/2026.10.21-task-brand`，提交 `e68b31635f6bf577881a695fe17f6ae117b9e092`。
- 生产对应版本 `2026.11.01-print-identity-e68b316`，诊断脚本核对该提交后才执行。
- 本次完成 UI 调整；订单查询重构、库存局部刷新属于提出的下一步方案，尚未实施或部署。
- 线上诊断通过现有企业登录权限请求订单；组件计时使用 MySQL 只读事务、限制 SELECT/WITH，未改生产订单、库存或配置。

## 实测

筛选：等待发运，2026-08-03 至 2026-11-01，每页 20 条，关闭列表附带的状态计数及物流选项；总记录 328。依次请求第 1、2、1 页。

| 采样 | 完整订单 HTTP | 核心订单 SQL | FBP 本地快照 | 拣货信息 | 利润版本标签 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 第 1 页首次 | 3844 ms | 6766 ms | 11 ms | 27 ms | 15 ms |
| 第 2 页 | 2537 ms | 1272 ms | 10 ms | 17 ms | 9 ms |
| 第 1 页重复 | 2110 ms | 850 ms | 7 ms | 37 ms | 10 ms |

完整 HTTP 与组件查询分别顺序测量，组件没有覆盖全部请求路径，不可相加或相减来计算精确占比。缓存和线上并发负载会影响结果，首次核心 SQL 慢于前一个 HTTP 也表明波动较大；这是三个样本，不是延迟分位统计。

已确认：

1. `orderRowsByIdsMysql` 的核心查询本身明显昂贵。它同时关联订单商品、SKU 映射、套装/配方、库存流水、采购分配、到货记录、利润已存结果和人员信息，再做多种聚合。
2. 列表 FBP 读的是本地 `ozon_stock_snapshots`，不会在翻页时现场调用 Ozon。仅隐藏这项不能解决秒级查询耗时。
3. 列表读取已存利润结果和版本标签，不会直接触发利润公式重算。表中的“利润版本标签”只是一项附加查询，核心 SQL 中利润关联的独立成本尚未隔离，不能据此宣称利润字段完全没有成本。
4. 库存顺序排序和物流筛选另有范围汇总路径，不能用本次普通日期排序样本代替这两种条件下的测试。

建议下一步：

- 对核心 SQL 取得执行计划，先限制采购/到货/库存子查询的范围为当前页实际涉及的库存和请求，核实一对多连接及聚合，避免放大行数。
- 将非首屏必要的明细改为按需读取；保留首屏已存利润数值，不改变利润公式。
- 单独验证库存顺序排序、物流筛选、深分页、冷/热缓存及并发；对照每单的利润、SKU 数量、套装部件和采购覆盖结果，避免仅提速但算错。
- 优先减少查询成本，再考虑按企业、筛选、页码缓存结果及事件失效。不能只增加一个可能陈旧的 Redis 值。

## 更新本地库存的刷新行为

当前 `OrdersTable` 保存实物后，`OrdersPage` 调用 `loadOrders({ forceRefresh:true, silent:true, includeCounts:true })`，会失效列表缓存并重读整页。这不是必须的业务要求。

建议让保存事件携带实际库存商品 ID，查出当前页所有使用该库存的订单（含套装、配方和配件），仅更新这些订单的库存事实和采购覆盖信息；其他页失效缓存，状态计数异步核对。已有 `/api/orders/inventory-availability` 批量接口可复用，但它只更新库存事实，不能独自代替全部采购覆盖/筛选状态更新。涉及缺货筛选的移入/移出应保留当前阅读位置，并提示用户刷新，不应悄悄重排整页。

## 本次 UI 调整

- 两个模式的按钮均单击直接切换；正常显示当前模式，悬浮显示切换提示。
- 查询紧邻订单搜索输入框；日期后是同步当前范围、拉取新订单。
- 主操作顺序为更多操作、批量备货、批量打印、OGL 发运、模式切换。
- 新批量备货只针对当前页可直接备货的 FBS，不使用跨页勾选，跳过 FBP 与需要单独拆单确认的订单。确认框显示数量和跳过范围。
- 等待确认或请求期间防重复提交；企业/权限变化、翻页导致当前订单不再可备货时中止。
- 保留原页面样式和小屏换行策略，保留固定分页与跨页选择摘要。
