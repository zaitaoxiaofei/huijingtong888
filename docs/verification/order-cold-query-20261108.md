# 等待备货／等待发运冷查询优化 — 2026-11-08

## 原因与边界

基线为发布分支 `release/2026.10.21-task-brand` 的 `0be0f90ca5d8df664e6b34578b75e524098673cf`。上一轮已经将桌面订单行与库存事实分开加载，但首次等待备货仍约 8.4 秒，未达到普通订单打开／翻页低于 2 秒、超过 3 秒不通过的验收目标。

本轮进一步区分数据库执行线程的 CPU、调度等待与主缺页。生产只读诊断中，一条旧核心查询约 8.05 秒超时，而对应线程 CPU 仅约 419 毫秒、主缺页约 10,823 次；后续完整对照也显示，长等待伴随大量主缺页，运行队列等待占比较小。这支持该组长尾主要受缺页读入等待影响，不能将全部墙钟归为扫描或优化器 CPU。

原查询的范围 CTE 被多处分支引用。独立实测核心语句需要约 168 个表句柄，而生产 `table_open_cache=2000`、`table_open_cache_instances=16`，每分片约 125 个缓存位置。真实编号触发器的表句柄对照也观察到反复开表与触发器对象膨胀。MySQL 的触发器调度对象属于 TABLE，每个缓存表句柄可持有自己的触发器编译副本；SELECT 的 READ ONLY 事务本身不会跳过新句柄的触发器加载。相关机制见 [官方表缓存变量](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html#sysvar_table_open_cache_instances)及 [MySQL 8.0.46 触发器缓存实现说明](https://raw.githubusercontent.com/mysql/mysql-server/mysql-8.0.46/sql/sp_head.cc)。

本轮减少普通订单核心查询的工作集，不调整生产缓存、buffer pool、触发器或其他数据库全局配置，也不以跳过库存、采购、利润事实或企业归属检查来换取速度。

## 实现

仅在普通有界摘要路径启用新方案：`summaryOnly` 为真、`coveragePromise === null` 且订单 ID 不超过 100 个。明细、依赖完整采购覆盖以及大批量旧调用继续使用原来的单条核心 SQL。

同一物理连接建立 REPEATABLE READ 一致性只读快照，依次完成：

1. 按原显式绑定优先、SKU 回退及产品归属规则读取当前页的订单项、绑定和产品 ID。
2. 按原产品组件／配方规则读取当前页实际需要的组件产品 ID 集合，保留企业归属、默认企业 NULL 行、去重和未启用产品的原有处理。
3. 核心查询用绑定的 `JSON_TABLE` 范围复用以上两个结果。只移除已被组件范围消费的配方产品范围定义，保留其余联接、投影、状态和数量计算。

两类范围 ID 均先在 MySQL 中 `CAST AS CHAR`，作为十进制字符串传递，再由 `JSON_TABLE` 声明为 BIGINT UNSIGNED，避免新增 JavaScript Number 精度损失。SKU 和店铺信息仍从原订单项／订单列读取，保留原字符串类型及排序规则。三个库存流水聚合仅固定内连接的范围优先顺序，不改变流水状态、库存位置或企业条件。

回调只包上述 SQL；独立库存余额、原始订单载荷和其他补充信息仍在其既有边界读取。完成后结束快照；语句错误保留原异常，清理失败的连接不回池。纯后台调用不为自己建立交互读取保护。

## 真实业务源回归

`test/order-core-item-scope-mysql.test.js` 使用冻结的 `0be0f90` 函数作为基线，候选直接调用修改后的服务及实际快照函数，没有通过代理改写候选 SQL。8 项检查全部通过：

- A／B／默认企业 NULL 归属，显式绑定与 SKU 回退，跨企业绑定和组件污染行。
- 单品、套装、配方、停用产品、零比例、多 SKU、摘要及完整明细的全部字段哈希。
- 订单项、绑定、根产品及实物组件的 ID 超过 `Number.MAX_SAFE_INTEGER` 后仍保留完整十进制值。
- 空订单项／空组件范围继续返回原有订单结果。
- 独立写连接在订单项预读后提交绑定变更：当前快照的组件和核心结果仍与旧结果完全一致，下一个快照确实读到新绑定；测试最后恢复数据并关闭连接。
- 明细、非空采购覆盖 Promise、超过 100 个 ID 的调用不增加范围预读、JSON 核心语句或快照事务。
- 全部订单、等待备货、等待发运的分页成员、总数及完整响应字段保持。
- 实际 runtime facade 的诊断接线与直接调用结果相同，不记录业务参数或响应正文。

包含 12,000 条无关订单／历史、60,000 条无关库存流水、13,600 个无关配方的隔离 MySQL 样本中，20 行完整服务读取约 224／220／222 毫秒变为 14.9／14.8／14.2 毫秒；纯核心查询约 215→7.3 毫秒。核心表句柄由 168 降到 52（对应 external_lock 调用 336→104）。这些是本地合成样本，不等同生产页面延迟。

新路径每次核心读取增加两个有界范围 SELECT，以及只读快照的建立／结束；没有声称 SQL 往返数减少。它减少的是大型查询反复展开、打开和访问的表对象及扫描范围。

## 生产只读查询对照

同一个新应用数据库连接、同一个一致性只读快照、固定语句时间，对当前企业归属范围内最新 20 条订单执行“新→旧→新→旧”。不清空生产缓存、不触发业务写入；各语句有限时保护，结果只保留行数与哈希。四次读取均为 20 行，全部字段哈希一致：

| 顺序 | 范围预读＋核心墙钟 | 对应线程运行时间 | 主缺页次数 |
| --- | ---: | ---: | ---: |
| 新查询首次 | 420 ms | 156 ms | 163 |
| 旧查询随后 | 5265 ms | 547 ms | 6502 |
| 新查询重复 | 185 ms | 109 ms | 93 |
| 旧查询重复 | 1355 ms | 248 ms | 1512 |

新查询首次的 420 毫秒包括两个范围 SELECT（约 11.5／17.0 毫秒）及核心 SELECT（约 387 毫秒）。此对照不包含 HTTP 鉴权、每次请求的快照建立／释放、独立库存回填、前端资源下载或 DOM 绘制；不得把 420 毫秒直接描述为整个等待备货页面的耗时。

线程指标从该应用 MySQL 连接对应的 OS 线程采集；不将整个 mysqld 进程的 CPU 归给单条查询，也不能覆盖其他线程承担的异步 I/O。第一次是在新诊断连接上的首次访问，并非人为清空了服务器或操作系统缓存。样本仍受后台负载、缓存先后和订单页组成影响。主缺页显著减少与时长下降共同支持工作集缩减的效果，但不能承诺所有页面固定提升相同倍数。

## 发布后验收

本文记录的是合并前的源码回归和受限生产只读查询证据。完整页面是否达到目标，必须以准确合并提交的发布结果另行验收：桌面等待备货、等待发运和全部订单的冷开／翻页，主列表先于库存回填，元数据并发时的长尾，手机原有列表兼容性，以及完整结果和企业归属保持。部署前不能声称完整页面已经修好。

部署继续使用 release 分支、准确构建提交和预期生产提交保护；不合并 main，不部署未提交覆盖层，不修改利润 V1 或库存账务规则。

额外检查 `tenant-orders.test.js` 时有两个既有源码文本断言失败（仍要求旧的直接企业解析和无第二参数的覆盖调用写法）。在独立、干净的 `0be0f90` worktree 执行原测试，同样两项失败；本轮未修改这两个生产函数或放宽这些断言。真实 MySQL 的企业归属、负向污染和完整字段验证单独运行，不能将源码文字匹配失败误报为本轮新增的数据隔离问题，也不宣称全仓测试全部通过。
