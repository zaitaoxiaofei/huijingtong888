## 手机真实接口

`MobileWorkQueue.vue` 默认每页 20 条，可切换 50／100 条；与电脑共用后端，逐入口独立验收：

| 手机入口 | 读路径与关键参数 |
| --- | --- |
| 登记采购 | `/api/products`，`paged=1&view=inventory&includeStock=0` |
| 必须采购／保障补货 | `/api/inventory-workflow/alerts`，`view=workspace&compact=1&task=required/advisory&snapshot_only=1` |
| 采购收货 | `/api/inventory-workflow/purchase-arrivals`，`status=pending&day_mode=pending`，保留采购日／日期范围 |
| 采购记录 | 同上，`status=all&recent=1` |
| 已入库菜单 | 同上，`status=received`，不加 recent 截断 |

普通翻页不触发重新核算。手动刷新／业务保存后的刷新使用 `refresh=1`；后台结果轮询使用 `poll_snapshot=1` 且删除 refresh，不重复启动核算。

北京时间 09:32:43 的线上基线：登记 56ms、收货 97ms、采购记录 93ms、已入库 130ms，均返回成功。必须采购／保障补货分别 55／82ms，但已有快照处于 stale/updating；约83秒后仍是 50／68ms 且 updating，未计入严格 fresh 验收。后续元数据表明已有一条快照成功更新，但未关联用户企业，不能据此认定该次慢刷新原因或宣布完成。当前连接池／I/O瞬时统计没有证实当时阻塞，后台通道修复的实际收益仍需上线复测。

## 本轮补齐的修复

1. 手机列表接入现有展示读取作用域。隐藏、KeepAlive 停用、卸载、切换账号／企业及 401／403 时取消列表 GET 和轮询；恢复可见／激活或经认证校验后只补查一次。scope-changed 到 auth-verified 之间，手动翻页／刷新及岗位 watcher 也不能抢先读取；已终止的晚响应不能覆盖页面。采购、到货确认、验收入库、物流保存及其幂等键不被展示暂停取消。
2. 需求快照的排队回调显式进入 `background` 工作通道，使 HTTP 发起的后台核算不再继承前台连接通道。产品枚举、计算及保存都使用该通道，不增加连接总额。实际工作台快照轻读、到货列表以及 `paged=1&view=inventory&includeStock=0` 的产品列表获得既有前台优先保护；需等待覆盖计算的重型读取不扩大该保护，避免依赖死锁。
3. 到货列表把重复的提醒事件 JSON 分组改为每请求一次，仅保留 inbound／product／reminder 三个数字。提醒人员／备注及拆分来源只按当前分页查询。仍先 MAX(id) 再核验 product／tenant；错误的新提醒不能让旧提醒重新出现。日期索引和数量汇总保留全部相关待处理批次，完整财务／仓库权限、套装审核、谱系、部分到货与真实入库语义不变。
4. 标准健康检查增加六个手机固定标签 `mobile_procurement_{register,required,advisory,pending,history,received}_paged`。可配置 1000ms 完整响应预算；PC及手机两个需求入口还要求 available、ready、非 stale／refreshing。采用未四舍五入耗时判定。失败以正常非零退出码结束，避免 Windows Node 强制退出时的 libuv 句柄断言。

本轮不改手机模板／CSS、采购与库存写入规则、索引、数据库结构、OSS存储策略或生产全局配置。到货列表仍保留全企业组成图和审核事件历史读取；冷首次快照恢复仍可能访问 OSS，不能宣称所有历史 I/O 或所有冷启动风险已消除。
