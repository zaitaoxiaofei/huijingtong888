# 采购列表一秒目标：接口口径、修复与验证

基线为 ECS 已部署的 `a4af631db413bdd9acb56a6c960072cea56a6e1b`。本轮仅在独立工作树修改后端读取与验收工具，未部署、重启或调整 ECS 配置。

## 实际页面与线上读数

采购工作台 `/procurement/workspace` 使用 `InventorySupplyWorkspace.vue`，默认请求为：

`GET /api/inventory-workflow/alerts?task=required&scope=all&page=1&pageSize=50&view=workspace&compact=1`

此前健康检查的 `/api/procurement/requests?grouped=1&paged=1&page=1&pageSize=30` 是兼容接口，不能用它的 16 秒代表现有主列表。两者业务契约、数据数量、快照状态不同，不能给出“16 秒降到 39 毫秒”的提速结论。

北京时间 2026-11-28，服务器本机通过标准健康检查的私有临时副本，串行读取实际主列表；副本只改配置模块的绝对导入位置，不改线上源码或配置，不回显登录人、数据库配置或业务正文：

| 时间 | 完整 HTTP 耗时 | 行数／总数 | 快照状态 |
| --- | ---: | ---: | --- |
| 09:03:00 | 217ms | 3／3 | available、stale、updating |
| 09:03:59 | 49ms | 7／7 | available、ready，非 stale／refreshing |
| 09:04:14 | 39ms | 7／7 | available、ready，非 stale／refreshing |

后两次达到当前账号、默认筛选、运行中进程的一秒目标。首测返回了已有快照，不能当作实时更新完成的结果。此测量不包含浏览器公网传输、页面绘制、服务重启后的 OSS 冷恢复，也不证明所有筛选或未来规模均低于一秒。快照表有一条 OSS 引用与一条内联记录，本轮未读取 OSS 正文、清缓存或改存储策略。

## 具体查询修复

1. 分组页及合法单商品查询先选取本次相关的 SKU 映射，以直接映射与店铺 SKU 两个索引分支合并订单明细事实。两分支只排除同一映射的重复命中；不同映射仍保留原 OR 关联的贡献。销量和全历史统计复用这份事实，保留所有原日期 CASE、未来日期、NULL、取消规则、全历史金额、数量与 `COUNT(DISTINCT order)`。
2. 库存商品的采购记录抽屉仍需图片、备注、紧急程度及金额等完整字段，不切换 compact。对原有正安全整数 `productId`／`product_id`，将同一商品限制下推到 SQL 外层及聚合，避免全部商品读回再过滤；分页、总数和原有字段保持一致。无商品限制、非法值或旧兼容调用沿用原行为。
3. 覆盖计算将逐订单项执行的最小 fallback 映射查询合并为本语句内按店铺／SKU 的映射表。保留直接映射优先、active、企业及默认 NULL 归属、WB 禁止隐式兜底和既有库存分配顺序。

没有增加跨请求 TTL、截断历史、减少接口字段、改 UI、索引、数据库结构或真实采购／入库写入。试验中的两级运输历史 MIN 没有减少实际读取，已撤销；不能把 SQL 形状变化当作性能收益。

## 本地证据

独立 MySQL 8.4.9 仅开命名管道、关闭 TCP，使用随机测试库和 128MiB buffer pool。数据均为合成夹具。

- 完整采购读取 oracle 对比冻结的旧实现：所有选择到的原始详情列、最终分组、分页、总数、优先级、默认 NULL／A／B 企业、共享／负数／停用组件、映射多匹配、日期边界，以及真实采购、部分入库结果均一致。单商品下推只与旧结果中同商品的原始行比较，最终结果仍逐项完整比较。
- SKU 关联独立实库对照含两个会话时区、NULL 映射／SKU／日期、未来和长期历史、同映射双命中、不同映射及同商品多映射、停用及外企脏关联。
- 五万条无关历史订单的局部聚合交替暖测中，中位耗时约 `389.41ms → 4.22ms`。执行计划确认直接映射和 SKU 分支使用现有索引；这只是聚合实验，不是整个接口的线上收益。
- 完整详情 SQL 的五万条追加事实实验中，旧版约 `305–323ms`、候选 `266–272ms`；相关商品的全历史仍参与统计，因此不能沿用无关历史实验的提速比例。
- 覆盖主需求 SQL 的合成暖测约 `29.9ms → 19.9ms`，Handler 读取 `20,116 → 14,110`；未证明整个实时覆盖计算低于一秒。
- 实际工作台 HTTP 路由在 1029 个合成商品下验证首次读取持久快照、50／100 行、第二页、外企商品不可见和撤权后拒绝。本机测得 `34／15／11／6／2ms`。包含真实 MySQL 企业权限校验和完整 JSON HTTP 传输；测试会话由夹具提供，不包含令牌中间件。测试持有独立库的只读表锁，确认后台重建待写时前台仍可读取已有结果；不对生产加锁。

扩大回归发现旧 FBP 覆盖夹具未包含生产启动添加的 `products.is_accessory`，在精确 `a4af631d` 工作树亦复现相同缺列错误。试补该列后，夹具中的跨企业套装组成又触发现有 409 保护；没有为通过旧夹具放松生产规则，已撤回试补，保留原测试不变。这一旧测试不列为本轮通过项；新覆盖实库 oracle 另行验证完整结果、默认 NULL／A／B、组合、外企拒绝及部分收货。

最终针对性验证共 85 项通过、无失败或跳过：真实 MySQL 回归 53 项、工作台／快照／诊断单元回归 26 项、验收预算回归 5 项、完整 HTTP 路由实库回归 1 项。正常前端构建、UTF-8、SQL 参数绑定、语法和 diff 检查均通过。旧 FBP 夹具的独立已知失败不包含在这 85 项内，亦未报告整个仓库测试全绿。

## 可执行的一秒验收

标准 `scripts/health-check.mjs` 增加实际采购主列表，支持固定标签白名单筛选、响应耗时预算和已完成快照校验：

```text
HEALTH_CHECK_LABELS=procurement_workspace_paged
HEALTH_CHECK_MAX_DURATION_MS=1000
HEALTH_CHECK_REQUIRE_FRESH_SNAPSHOT=1
```

凭据仍走既有健康检查环境变量。测量从请求开始到完整响应体读取并解析后结束；上述组合要求 HTTP／分页合同正常、快照 available 且 ready、非 stale／refreshing，响应不超过 1000ms。超时预算或快照未完成均以非零退出；不把 warming 空页当达标。未知标签在发送登录凭据前拒绝。未设预算时保留常规健康检查行为。

上线需按 AGENTS.md 获得本轮新批准，重新合并精确提交并从干净 release 工作树构建。上线后使用上述严格组合串行复测真实主页面；兼容 grouped 接口的 fresh 全量核算继续单列，尚不能承诺其低于一秒。
