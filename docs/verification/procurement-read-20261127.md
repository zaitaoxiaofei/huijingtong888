# 采购分组读取优化与验收边界（2026-11-27）

## 基线与现状

基于发布分支 `4650f54b`，与 ECS 已部署 `67e3563c` 的运行时代码相同，差异仅为存储分层文档。原生 Git fetch 曾两次返回空响应，先通过 GitHub 连接器确认分支 SHA，随后原生 fetch 成功确认同一基线。

上一轮常规健康检查的分组采购接口首次超过 15 秒；放宽观察窗口后返回 200，但仍约 21.236 秒。返回成功不代表性能问题已消失。本次只修改后端读取和诊断，不改变 UI、采购写入、库存真实性、利润算法、OSS 对象或存储类别。

生产只读诊断显示，采购申请约 1.05 万行、商品约 1029、订单约 3.67 万，主要业务索引存在。Performance Schema 是自 11 月 16 日起累计统计，并非该次请求的完整追踪：

## 已实施的最小修复

1. 分组页的组件库存与待到货聚合只处理本页父商品关联的直接组件，保留原有企业、状态、库存位置与组件有效性规则。非分组旧读取不施加分页组件限制。
2. 销量聚合增加等价 UTC 时间下界。原有指标最远只使用 `CURRENT_DATE - 29 DAY` 起的北京时间日期，旧行在全部 CASE 中均为零。保留原有 CASE、未来日期行为、NULL 与取消状态处理、SKU 映射 OR 的多匹配含义，以及全历史采购、出库和订单统计。
3. 采购 facade 复用现有安全诊断，只在请求超过一秒时记录固定阶段和数值／布尔计数：scope、schema、coverage、filters、page_ids、details、projection、workflow、gaps。日志不含企业、商品、订单、查询参数、SQL、异常正文或响应内容。日志与时钟失败不能改变返回值和原异常。

不截断历史覆盖，不延后实际采购缺口，不加入跨请求 TTL 掩盖旧数据，不修改调度、基础索引或生产全局配置。

## 等价与性能验证

独立 MySQL 8.4.9 使用关闭 TCP 的命名管道和随机测试数据库。完整提取 `git show 4650f54b` 的原函数作为 oracle，与候选完整函数执行同一夹具；比较所有原始详情列和最终返回值，而非只比较行数。

覆盖全／compact 分组、分页总数、空页、筛选和优先级、A／B／默认数值与历史 NULL、非分组读取、共享／负数／零／停用及外企组件、SKU 多映射、未来／NULL／29 日边界前后一秒，以及真实采购与部分入库后的订单缺口。数据库时间固定；独立 SQL 预热后交替执行旧、新、新、旧，避免把旧冷缓存与新热缓存当成收益。

约五万条合成事实的详情 SQL 对照中，Handler 读取计数总量从 165,854 降为 60,330，约减少 63.6%；一轮暖读旧版约 433／456 毫秒，候选约 294／299 毫秒。访问路径显示销量可走 ordered_at 范围、组件可走 product_id 查找；部分物化分支未实际执行，不能用其估计值替代真实扫描证据。这只是详情 SQL 的本机对照，不能外推为完整采购接口固定提速或线上 21 秒已解决。

五个旧 source-shape guard 在物理 `4650f54b` 基线与候选均失败，失败标题完全相同；另两项旧 UI 函数提取断言也与后端改动无关。保留这些边界，不为通过旧断言修改 UI 或采购业务规则。

本轮针对性单元回归 40 项、独立真实 MySQL 回归 32 项，共 72 项通过、无失败或跳过；正常前端构建、UTF-8、SQL 绑定及 diff 检查通过。旧完整采购夹具在精确基线也因缺少当前必填计量包装而提前失败，仅为测试商品补合法包装数据，保留全部原断言及生产校验，随后完整采购／部分收货／企业隔离回归通过。

## 资源与上线边界

生产 InnoDB buffer pool 当前只有 128MiB，运输历史表与索引约 855MiB，原始订单表约 269MiB；历史累计存在空闲页等待和大量物理读取。但累计值不能证明当前阻塞，既有文档也记录过触发器表缓存及 swap 膨胀。本次不据此盲目扩容缓存、不重启 MySQL；任何调整需结合当前进程内存、swap、磁盘等待及真实分段数据单独审核。

尚未为本轮部署、重启 ECS 或修改生产配置。按根目录及模块 AGENTS.md，取得针对本轮的明确批准后，重新核对生产提交、合并最新 release，并构建精确合并提交。上线后验证同一权限、同一筛选的返回结构、总数、顺序与数量，记录实际阶段耗时；不能用单个 SQL 局部收益替代端到端验收。
