# 订单查询、明细延迟加载与库存局部刷新

## 基线和范围

从远端 `release/2026.10.21-task-brand` 最新提交 `ff742a6058fc023d2e053828556a19e4a8ce2756` 创建 `codex/order-page-query-local-refresh`。保留 PR #61 的模块工作台调整，未改其页面和路由。提交前又将远端最新 `8b6875f67090cc5bd4d2e42271f78e45799ba142` 的 OGL 批量标记与手动发运功能合入本任务分支；三个已验证的查询/刷新函数未被该合并修改。本次尚未合并回 release 或部署。

实现用户选择的 ① 查询优化、② 关键数字保留/明细按需加载、④ 库存更新只刷新相关行；没有增加 Redis、后台全页刷新或修改利润公式。

## 查询改动

- 原 SKU 映射使用“绑定 ID 或店铺 SKU”的 OR 连接，执行计划显示映射表全表扫描。
- 改为先解析一条映射：优先当前企业、同店铺的有效显式绑定，失效或缺失时回退到同店铺 SKU 的有效映射。与现有库存数量接口的规则保持一致。
- 当前页订单商品映射先去重形成 CTE，后续按主键复用；库存排序使用同样的优先级，避免排序和展示不一致。
- 配方库存流水汇总限制到当前页涉及的子产品，避免汇总其他产品。
- 分页请求使用 summaryOnly：保留金额、预估/实际利润、SKU 数量、库存、采购在途数量和时间、状态；费用拆解、人员、历史采购/快递信息不在首屏查询中聚合。采购人员的企业成员检查等连接在明细路径保留。
- 保留现有订单详情和采购批次接口，点击时读取完整内容；没有将未加载明细伪装成真实零值。完整兼容路径默认不启用 summaryOnly。
- 只读对照中，常规订单保留字段与旧查询一致。历史绑定 ID 与 SKU 回退恰好同时命中不同商品时，旧 OR 可能重复聚合；新规则按明确绑定优先，仅统计一次。独立数据库用人工预期值验证这类情况，不能机械地保留旧重复结果。

| 等待发运，第 1 页 | 4762 ms | 1293 ms | 无 |
| 等待发运，第 2 页 | 1801 ms | 608 ms | 无 |

## 局部刷新与准确性

- 库存弹框保存事件携带当前实际库存 ID，包括弹框内切换过的商品。
- 沿用 `/api/orders/inventory-availability`，增加明确的 includeRows 请求；普通库存数量查询保持原契约。
- 服务端先验证当前页所有订单归属，再按真实 SKU/配方/套装关联找出受影响订单。共享配件关联的订单全部纳入；套装保留其他子产品的完整数量信息。
- 对受影响订单涉及的产品重新执行现有采购覆盖算法，包含这些产品在其他订单中的竞争需求，不按当前页片面分配库存。
- 前端仅替换返回的相关订单对象，不重新请求订单列表，不改变排序、分页、当前总数或跨页勾选。其他页和状态计数缓存失效，提示手动刷新查看新的筛选成员与数量。
- 库存保存后核对期间，旧的本地数量及采购覆盖显示待核对，暂停依赖这些信息的备货/采购入口。失败时保留待核对提示和重试按钮，不能把旧值或缺失值作为最新值。
- 保存时取消旧的列表/数量请求；翻页、企业或会话变化后丢弃旧响应。连续保存第二个库存时，连同前一个中断的更新一起核对。

## 验证结果

- 合入并行 OGL 改动后，56 项专项与 OGL 回归测试通过：当前页批量备货、打印回归、局部库存读取、部分行更新、库存刷新失败/重试、保存后翻页、连续保存、会话与企业隔离、分页排序。
- 独立、关闭 TCP 的 MySQL 中，相关测试最终 35 项通过：新增 6 项摘要/排序/真实库存关联测试、4 项搜索测试、25 项既有订单企业隔离测试。首次测试包漏传两份前端源码导致一项文件缺失；补齐后对应搜索套件全部通过，不属于业务结果差异。
- 实际 Vue 页面 + 模拟 API 浏览器回归通过：共享配件保存为 20 件后，单品实物更新为 20，使用两件配件的套装更新为 10；无关订单不变。三张已加载的主图 DOM 节点不被替换；主订单列表仅请求一次。利润详情仅在点击后请求，Vue 错误记录为空。
- 浏览器验证遵守用户要求等待财务预览释放 8788，没有终止其他窗口的预览进程。测试结束释放本次预览端口和浏览器空间。
- Vite 构建、UTF-8、SQL 绑定、前端安全检查及 diff 空白检查通过。构建写入临时目录，未覆盖已部署文件。
