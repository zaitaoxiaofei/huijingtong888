当前结构值得先讨论的差距

企业归属有多套表达部分核心表使用数字企业 ID，AI / 刊登等表保留字符串键及历史兼容值。NULL、admin、公共项不是同一含义，不能统一批量替换。
字典的可见范围与唯一键需要一起设计部分命名选项已读公共项＋本企业项，但旧全局唯一键仍存在；分类、车型资产等又分布在不同字典中。先确认同名、覆盖和停用规则，再改结构。
关联完整性主要依赖业务代码只有两条数据库外键。需要逐链检查父子归属、自然键、事务及后台任务；不宜直接给所有同名 ID 加外键。
工资模块仍需明确企业边界五张工资表存在公司、人员与政策关联，但快照没有企业字段，已查服务 SQL 也缺少企业上下文。需联合权限和完整调用链验收，本轮没有复现生产越权。
历史冲突不能由当前平台状态自动裁定库存数量、人工收货、成本和已锁定利润是 ERP 内部业务事实。Ozon 当前状态可以重新拉取，但不能恢复这些事实。

不必把 219 张表都当作核心业务表维护

其中既有业务主表、明细、任务、审计，也有缓存、兼容设计和日期备份。可以精简，但目标应是减少重复概念与维护路径，而不是先定一个删表数量。

第一批最清晰的是 2 张日期备份＋4 张旧上架流程表，先做归档／停用核查。它们是候选清单，本轮没有迁移或删除，也不意味着其他表不能继续优化。

订单、分批实收、采购分配、库存流水、外部回执承担不同事实，拆开有必要。配置和缓存则可以先统一归属、接口、刷新与保留规则，物理合表要在语义一致且有收益后再决定。

表快照行数
空表也可能是仍在使用的任务队列；没有静态引用也可能有旧版本或外部脚本依赖。generated_images 和品牌素材表仍有数据，generated_titles 还有当前写入，不能因名称类似就一起删除。

这些职责不建议为了少表而合并

  • 全局账号、企业成员、平台授权：分别管理登录身份、企业岗位和平台特权。
  • 本地库存商品、Ozon 在线商品、SKU 配方／绑定：同企业多店共库存依靠这些连接，身份不能混成一个 ID。
  • 采购申请、采购单、分批实收、数量分配、库存流水：保留数量与金额的完整来源。
  • OGL 申请、实际交运、平台进入运输：保留各阶段事实和外部回执。
  • 发布任务、发布明细、Ozon 回执，以及财务结果、锁定利润、历史修订：保留重试与追溯能力。

少表不等于页面变快

优先检查草稿与订单页面实际参与的 SQL、企业筛选、索引、COUNT、关联计数、大 JSON、图片处理和并发任务。移走一张不参与查询的旧表，不会直接减少这条查询的成本。

如何进入实施

  1. 核对候选的所有消费者、外部工具、旧版本和恢复用途。
  2. 统一业务定义与权威入口，先停止已确认的旧写入并观察。
  3. 给出迁移差异、原值归档与回退方案；业务含义不明确时先讨论。
  4. 完成企业 A/B、撤权、重试与重启验证后，再决定停用或物理合并。

本轮没有线上读写热度、实时行数和空间测量，不承诺减到某个表数或提升百分比。所有结论为本地结构与源码分析。

建议按四层讨论隔离，逐链验收

  1. 归属：记录属于哪个企业，店铺、父单、子项是否一致；平台公共资源采用明确范围，不能用“缺少企业字段”代表公共。
  2. 授权：登录身份、平台授权、企业成员、岗位职责分开；查询、修改、导出、附件下载分别检查。
  3. 执行：任务提交、排队、锁等待、重试、重启恢复均复核企业与成员；缓存键、任务领取和外部回执也必须带归属。
  4. 完整性：企业字段、自然键、幂等、数量台账、不可变历史一起校验。默认企业和客户 A / B 使用同一套验收规则。

这是后续工作建议，不是本轮已执行或已通过的验收。

已确认的两项细则

  1. 员工可见范围：普通员工默认可见本企业全部店铺；库存和采购在本企业共用。可见店铺不等于拥有管理、发布、付款或修改权限，具体操作仍按岗位授权。
  2. 公共字典更新：历史商品和单据保留原定义，新建时使用最新公共定义；不因公共字典更新自动覆盖历史记录。

后续仍需讨论的业务细节

  1. 岗位字段权限：库存成本、利润、财务等敏感字段如何按岗位显示？“全部店铺可见”不自动代表这些字段全部开放。
  2. 字典同名补充：企业补充项如何处理同名、覆盖、停用或申请成为公共项？稳定 ID、修订和快照属于实现建议，具体方案待讨论。
  3. 异常处理方式：是否采用“待核对队列＋只暂停受影响的写入”？谁负责确认库存或财务冲突，谁可以批准修正？
其他待明确边界

店铺更换企业时历史归属如何保留；SKU 换绑是否仅影响新单；企业案例和 AI 模板是否允许公开；成员离职后的私信保留；财务结账与更正制度；后台任务的数据保留期限。以上均未擅自制定或实施。
