## 一套 ERP，区分通用功能与汽配扩展

| 层次 | 面向业务 | 数据边界 |
| --- | --- | --- |
| ERP 基础 | 订单、库存、采购、采集、草稿、发布、财务 | 每企业私有；同企业多店共享既定业务资料 |
| 通用 AI | 商品识别、事实确认、文案、主图与详情图优化 | 企业素材、结果、任务及提示内容私有 |
| 汽配扩展 | 车型库、适配、车型裂变、汽配命名策略 | 公共基础目录＋企业补充；企业案例不公开 |
| 内部工具 | 本团队专用批处理和运营工具 | 按企业功能开通，不默认向客户开放 |

功能开通表示“企业买了哪些能力”；岗位权限表示“员工能做什么”；企业隔离表示“只能接触谁的数据”。三个判断都要覆盖 API 和后台任务，不能只隐藏菜单。当前已有功能配置字段，但尚未形成完整的模块开通控制。

不要为汽配和通用品类复制两套 ERP，也不需要每个行业一个数据库。先从通用流程中抽出车型和汽配提示策略；通用商品无需强制填写车型。

## 草稿：定义复用，填写内容独立

### 现有结构是什么

- 公共类目、属性、字典值已有 `ozon_category_mappings`、`ozon_category_attributes`、`ozon_attribute_values`。
- `listing_category_templates` 并非纯公共类目定义：它含企业标题、描述、图片、填好的属性、来源店铺和原始商品。它更接近“企业商品母版”，不能直接对所有企业共享。
- 草稿 ID 与 `template_id` 已分开。草稿仍同时保存 `template_payload_json`、`manual_facts_json`、`ai_payload_json`；创建和裂变时多次展开同一事实，确有去重空间。
- 采集箱按企业＋SKU 更新已有行，不是每次编辑都新建一行。原始采集包和人工编辑内容仍有重叠。

### 建议目标

```text
公共类目定义版本：有哪些字段、必填规则、选项引用
        ↓
企业商品母版版本：本企业可复用的事实和素材
        ↓
具体草稿：独立 ID、定义/母版版本、自己填写的内容和图片引用
        ↓
店铺副本：offer、价格、水印、文案等店铺覆盖值
        ↓
提交记录：本次实际提交的冻结请求及 Ozon 回执
```

例如同一类目裂变 100 个车型，公共字段定义只存一份；每个草稿只存各自车型、文案、选中属性及媒体引用。相同不可变素材可以复用，每个结果的图片顺序和主图仍能独立修改。

关键约束：

1. 草稿 ID 是具体商品记录；共享的是**模板 ID 和版本**。公共定义更新不得悄悄改掉旧草稿。
2. 类目可变属性保存一个小 JSON 合理；搜索、筛选、排序的常用字段单独结构化。不要把每个属性拆成大量行，也不要把所有内容再次包进一个巨型 JSON。
3. 复制和裂变引用冻结版本，不依赖会继续修改或被删除的母草稿；避免层层差异链，保证每个结果能独立还原。仍被草稿或发布记录引用的版本，不能因为母版或采集记录被删除而物理清除。
4. 图片已设置、尚未设置、人工明确清空是三种不同含义。保存主图、顺序、生成版本和人工意图，不能空了就回退到旧模板图片。
5. 图片/视频文件可在 OSS；数据库仍需保留媒体身份、用途、企业归属、顺序及读取引用。公开刊登地址与私有原素材访问边界不同。
6. 发布时冻结实际请求一次，不能只引用会变化的当前草稿，否则以后无法查清“当时究竟提交了哪八张图”。大原文可校验后压缩冷存，列表无需读取。

### 应当调整的部分

- 无变化的小时同步不重复保存相同客户/物流事实；只更新核验时间。真正状态变化保存小事件。
- 已有历史去重的 off/shadow/enabled 机制，代码默认 off，本轮未核实生产配置。部分报表依赖快照条数，必须先改为按订单/有效事件统计，对照一致后再启用跳写。
- 当前物流、店铺、日期、状态等筛选走结构化列和匹配索引，避免为一次搜索加载大范围原始 JSON 后在应用层过滤。
- 完整订单号优先等值查询，前缀与模糊搜索分别走明确路径，避免所有输入都使用包含匹配。
- 库存、采购覆盖和状态计数采用可核对的增量摘要；普通翻页不反复重算企业全部采购。摘要丢失能重建，来源变化会失效，不牺牲数量准确性。
- OGL 当前申请快照＋订单成员引用保留；“状态没变的刷新”更新检查时间及失败计数，实际创建、确认、交运、撤回事件保留。申请成立和进入运输继续分开判断。
- 利润当前值维持一份，确有变化的输入/计算版本保留。大历史版本可以冷存，不改冻结的 V1 利润公式。

目标是“当前订单一份＋必要变化事件＋独立库存/资金事实”，不是把库存流水、收货、实际交运也覆盖成最后一条。否则无法解释库存为什么少了、采购收了几次。

## 对外 AI：企业钱包与供应商成本分开

现在供应商密钥保存在 ERP 服务端，员工并没有拿到上游账号。现有企业月度次数限制已做；缺的是充值、冻结、扣积分、补偿和对账。部分内部成本按固定单价乘调用次数估算，不能直接改名为客户账单。

建议先形成一个明确 AI 服务模块，再独立部署；不必同时引入多层微服务和另一套人员系统。

```text
企业员工 → ERP 校验人员、草稿和企业
         → AI 服务验证服务身份与企业 AI 账户
         → 报价并冻结积分 → 调供应商 → 保存回执
         → 结算/释放/待核对 → ERP 使用结果
```

ERP 负责业务资料、员工和任务入口；AI 服务负责企业钱包、价格、供应商密钥、请求与结算。企业身份由 ERP 服务端签署，浏览器不能指定别人的钱包。跨服务使用稳定企业标识，不把本地数据库 ID 当作全球唯一身份。

建议最小五类数据：企业账户、积分流水、客户任务、上游尝试/回执、价格版本。充值先人工入账并保留唯一收款编号；自动支付以后接。余额由流水核对，不能只修改一个余额数字。

收费方案建议：

- 提交前说明积分价格，并保存该次价格版本；重复点击返回同一个任务，不重复扣费。
- 一个客户任务可能有多次上游尝试；平台重试成本与客户收费分别记，不因内部重试直接多扣用户。
- 明确失败按约定释放积分；超时但供应商是否接单未知时显示待核对，持有原回执，不盲目退款重投。
- 钱包、任务与积分流水事务一致；扣费账写不进就不能放行新的付费请求。人工补偿另记流水，不抹去原账。
- 成员停用、企业到期或额度不足后阻止新请求及新重试；已发生的供应商成本照实记录。
- 默认企业可保留内部成本模式；外部企业使用预付积分。两种模式共用调用入口，账务含义明确分开。

先迁移一条图片优化链，再迁移文案、裂变、矩阵。未迁移入口继续受现有企业权限和次数上限控制，不能开放一个绕过钱包的付费旁路。

| 必填项 | 示例含义 |
| --- | --- |
| 对象及企业/店铺 | 哪件商品、哪个历史状态或缓存 |

备份按价值分级：人工草稿/素材选择、库存和采购凭证、SKU 绑定、手工成本、财务、权限配置等优先保护；官方可重拉缓存可接受重建。Ozon 最新接口不能重建旧时点全部状态，也不能重建人工业务资料。

这不再要求每种小清理都先复制整库。具体执行方案按受影响范围给出备份和恢复方式。但现有三个键已存在“声明唯一却含重复”的问题；“允许丢弃旧重复行”不意味着直接 DELETE 一定能修好存储结构。旧严格修复工具的执行门禁仍有效，不能临时关闭检查绕过。后续若改为较轻方案，需单独实现和验证：修复目标范围、引用完整、有效唯一键，以及目标数据的可恢复性，再提交具体清单。

| P1，先做 | 草稿、订单/OGL、商品同步的查询与调度提速 | 已有分页/轻量化及局部优化，仍有重查询 | 中等，可逐接口交付 | 记录相同数据下冷/热页面耗时；前台不等待全库计算；多企业后台任务不占满连接 |
| P1，并行准备 | 历史候选清单与定向清理 | 分组和部分业务决定已有；未执行新清理 | 简单重复较小，错误引用需核查 | 先看删除清单；清后绑定/数量正确、唯一键有效、可恢复 |
| P1，结构阶段 | 草稿公共定义/私有母版/填充值分离 | 仅本次方案，尚未改新模型 | 中到较大，兼容迁移是主要工作 | 复制/裂变不复制完整定义，编辑及发布内容一致、主图不回退 |
| P1，对外收费前 | AI 企业积分服务 | 仅次数限制和内部估算；钱包未实现 | 中到较大，属于新增业务 | 人工充值、报价、冻结/结算、失败补偿、重启和重复请求可对账 |
| P2 | 旧表退役、重复目录和任务机制收敛 | 已有简化候选，未执行删表 | 分批中等 | 无消费者后再退旧表，业务含义不被强行合并 |

实施分批：

1. 先量化并解决当前草稿和订单/OGL 热查询，顺带测商品同步和后台任务抢连接；生成历史删除候选，不执行删除。
2. 再做订单历史止增、列表摘要和草稿新写入去重；新旧读取兼容，每次只切换一条业务链。用户确认后的历史清理独立发布，不与新钱包一起上线。
3. AI 模块开通、收费规则和接口设计并行审阅；实现最小积分服务后先用内部企业验证，再迁移各生成入口。
4. 逐批迁移旧大字段，冷存读取与内容哈希核验完成后才清热字段；不要同时重写整个 ERP。
5. 最后用代表性 4–10 企业、10–30 活跃用户数据，覆盖冷/热缓存、前台操作与后台同步/生成/发布。容量结果与小量真实 Ozon/AI/媒体验收分别记录。

不再把“未真实核验发布后的商品图片和数量”说成“员工权限还没完成”；也不把“尚未做容量验收”说成“当前业务数据不准确”。真实验收要确认最终商品内容、图片张数/主图、采购分次收货数量、一次发运与一次外部发布结果，验证具体业务结果即可。
