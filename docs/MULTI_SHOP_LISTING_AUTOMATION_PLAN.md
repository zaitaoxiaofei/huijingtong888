# Multi-Shop Listing Automation Plan

## Goal

Build an Ozon multi-shop listing accelerator on top of the current ERP. The operator prepares one product asset set, then publishes it to many Ozon shops with shop-specific images, watermarks, offer IDs, pricing, and validation.

The system should reduce manual listing work to the cost-sensitive inputs:

- price and target profit
- dimensions and weight
- color
- specification/model
- quantity and stock strategy
- source images

Everything else should be generated, validated, and queued by the system where possible.

## Product Model

Do not treat the product master as a single fixed listing template. The smarter model is category-driven:

```text
Ozon category
  -> category listing template
  -> AI attribute rules
  -> required Ozon attribute map
  -> image rules
  -> title and description rules
  -> shop-specific publish copies
```

### Category Template

Each Ozon category gets a reusable template:

- category ID and category name
- required Ozon attributes
- optional Ozon attributes worth filling
- attribute source type:
  - manual required input
  - derived from cost input
  - generated by AI
  - fixed default
  - shop override
- title prompt template
- description prompt template
- image requirements
- validation rules

Examples:

- color: manual input
- size/spec: manual input
- package weight: manual input
- brand: fixed default or AI
- material: AI, with manual confirmation
- usage scenario: AI
- search keywords: AI
- rich description: AI

## Listing Workflow

### 1. Create Product Draft

The operator selects a category and enters only high-confidence facts:

- source SKU or internal product code
- source images
- cost
- dimensions
- weight
- color
- specification
- stock quantity
- procurement URL or supplier note

The draft stores original images separately from generated shop images.

### 2. Apply Category Template

The selected category template expands the draft into a structured Ozon listing candidate:

- required attributes
- recommended attributes
- title candidates
- description draft
- keyword set
- image checklist
- validation checklist

Missing fields are marked as one of:

- can be generated by AI
- needs operator input
- blocked by Ozon category requirement

### 3. AI Fill

DeepSeek can be connected as a backend service, not called directly from the frontend.

Backend responsibilities:

- keep API key in server environment/config
- send category, known facts, images metadata, and template rules
- request strict JSON output
- validate returned JSON against the category template
- store AI result with prompt version and confidence
- require manual approval for risky fields

The first AI version should fill text and structured attributes only. Image understanding can be added later if needed.

### 4. Generate Shop Publish Copies

The operator selects target shops. For each shop, the system creates a publish copy:

- shop ID
- shop watermark
- generated watermarked images
- shop-specific offer ID
- shop-specific price
- shop-specific title variation
- shop-specific stock/warehouse strategy
- publish status
- validation result

This should reuse the existing shop watermark and image-cropper capabilities.

### 5. Preflight Validation

Before any Ozon API upload, each shop copy must pass validation:

- required category attributes completed
- image count and image format acceptable
- watermarked image files generated
- offer ID unique per shop
- price and currency present
- dimensions and weight present
- shop API credentials available
- stock quantity valid
- title and description generated

Validation should be shown as green/yellow/red:

- green: ready to publish
- yellow: publishable but should review
- red: blocked

### 6. Publish Queue

Publishing should run through a backend queue:

- submit ready shop copies in batches
- throttle Ozon API calls
- record request payloads and responses
- retry only safe failures
- allow resubmitting failed shops only
- sync final product state into existing online-products tables

## Suggested Tables

Names can be adjusted to match the existing schema style.

```text
listing_category_templates
listing_template_attributes
listing_drafts
listing_draft_images
listing_draft_ai_runs
listing_shop_copies
listing_shop_copy_images
listing_publish_jobs
listing_publish_job_events
```

Important fields:

- category template stores Ozon category ID and attribute rules.
- draft stores the one-time product facts.
- AI run stores prompt version, input snapshot, output JSON, and approval state.
- shop copy stores per-shop differences and publish status.
- publish job event stores every Ozon response for debugging.

- Category sync now follows the same official chain as the reference project: `/v1/description-category/tree` is cached in `ozon_category_mappings`, `/v1/description-category/attribute` is cached in `ozon_category_attributes`, and dictionary values from `/v1/description-category/attribute/values` or `/values/search` are cached in `ozon_attribute_values`. These tables are intended as a system-level Ozon category library, not a listing-only helper.

Patterns worth carrying forward:

- Variant rows should be edited in a dense horizontal table, not in separate cards.
- Repeated per-variant fields need a header action such as "same as first row" or batch fill.
- Image cells should show the first few images plus an overflow count.
- Copying an online product should preserve original SKU/offer information as reference only; the new listing `offer_id` should start blank or be regenerated.
- Rich content and attributes should be collected and stored as structured edit-state data before being mapped to Ozon import payloads.
- Final submit payload should follow the reference `ProductEdit.jsx` shape: each variant becomes one `items[]` row with `offer_id`, `name`, `description_category_id`, `type_id`, price, dimensions in `mm`, weight in `g`, `primary_image`, remaining `images`, `attributes`, and optional video/rich content `complex_attributes`.
- Local upload paths are useful for editing preview only. Ozon imports images by URL, so before formal submission any `/uploads/...` media must be converted to an externally reachable URL or another Ozon-supported media URL.
- In this ERP, listing media uploads are stored under `public/uploads/listing-media`. Set `LISTING_MEDIA_PUBLIC_BASE_URL=https://your-public-domain` (or use a non-local HTTPS `APP_BASE_URL`) so upload responses include a `publishUrl` that Ozon can fetch. The server intentionally allows public `GET /uploads/listing-media/...` access because Ozon cannot send ERP login cookies when it imports media by URL.
- The collector plugin gets the most complete data because it runs inside the logged-in Ozon browser page and reads Ozon frontend widgets with the user's cookies. This project should accept that collected payload through `POST /api/local-plugin/collected-product-details`, then convert it into a reusable local template.
- If the old collector plugin is reused, update its local API target from the reference app port to this ERP server, for example `http://127.0.0.1:8787/api/local-plugin/collected-product-details` when the local server runs on port `8787`.

Do not directly copy React/Ant Design components into this Vue/Element Plus app. Translate the interaction model into the current admin shell and keep the current backend as the source of truth.
