# 采购需求快照与非阻塞读取

基线：release/2026.10.21-task-brand @ 152d77b3d72b3af77348083e4c3632b3816b1bf4，保留 PR31 收货/FBP 界面改动。分支 codex/inventory-demand-snapshots。本版本尚未部署。

## 问题与行为

上一版虽已将超时恢复至约10–17秒，但订单、库存同步会不断增加全局工作流revision，短缓存失效后页面仍等待全量历史与FBP核算。

现在工作台直接读取本企业最近成功的持久化数值快照。业务变化只标记读取结果过期，不清空成功结果；后台按企业合并核算，当前进程只同时处理一个企业，SQL最多占用两个连接。自动核算每个活跃企业最多每分钟启动一次，静默数据五分钟后续算。当前仍复用完整统一算法，不声称实现单商品增量计算。

后台只在有人读取时激活；可见页面每分钟轻量刷新，核算进行中每三秒查结果，切走/隐藏/卸载停止，返回后再读。重启后先读数据库已有结果再后台核对。第一次没有成功结果时立即返回warming、空rows和null总数/任务统计，不把未知显示为零需求。

“刷新库存需求”读取快照；“重新核算”请求后台校准，可绕过自动合并间隔，并与正在运行的任务合并。旧任务期间发生变更并收到显式校准时，只追加一次后续任务。核算或持久化失败保留原结果及时间，显示可重试提示，不把失败缓存为无需求。

展示北京核算时间及更新状态。快照不存申请人、申请明细、FBP SKU行或采购费用，当前页来源/人员按实时企业权限重新查询；停用或迁出商品由当前企业实物列表过滤；申请取消、解绑等变化后的数量由后台更新，旧结果持续显示核算时间和过期状态。登记采购前另查单库存fresh状态，重新预填件数；需求已覆盖或未核实会阻止沿用旧预填。库存事务、利润V1、验收和成本算法未改变。

## 存储与上线

新增inventory_demand_snapshots表，仅tenant_id主键、计算版本、payload_json和calculated_at。每企业覆盖一份结果，不追加历史。计算口径发生不兼容变更时必须提升INVENTORY_DEMAND_SNAPSHOT_VERSION，旧版本结果不能作为当前数值读取。

专用脚本 scripts/init-inventory-demand-snapshot.mjs 默认只读检查；--apply仅创建缺失的缓存表并验证列与tenant_id主键，不ALTER、不清理/回填订单库存。也已纳入正常INVENTORY_FLOW_SCHEMA。启动就绪前只读检查该表，未初始化时不能完成发布切换。

需用户确认创建缓存表及部署后，再拉取最新release、合并分支、从确切合并提交构建。使用该提交的专用初始化脚本只建缓存表，再走标准ECS候选/正式部署；无需运行全套历史修复。回滚应用可保留缓存表，旧版不会使用它。

## 验证

独立socket-only MySQL使用681库存/5000订单规模数据。连续工作流失效时5次实际API读取合计约17ms；这是本地合成数据，不承诺生产延迟。回归覆盖首次warming/null统计、重启持久化、失败保留、并发合并、变更后续算、双查询限流、企业隔离、撤权后来源不泄露、单商品数量对照以及创建缓存表的默认只读和幂等。

133项相关回归（含专用迁移测试）通过，2项浏览器测试通过。浏览器覆盖缓存时间、后台更新、手动校准、数据已覆盖阻止重复采购、企业切换、无快照不显示零需求、失败保留和原库存流程图。前端构建、UTF-8、SQL绑定、前端安全和API文档检查通过。
