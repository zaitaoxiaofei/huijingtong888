# 草稿图片来源与继承规范

## 1. 目的

同一商品可能同时保留采集箱原图、模板图片、草稿公共图片、SKU 变体图片和 AI 生成图片。若各业务页面自行拼接这些字段，历史采集图可能覆盖用户后来在草稿中上传的图片。

本规范定义草稿当前图片的唯一解析规则，以及 AI 裂变、复制、发布时的继承边界。

## 2. 字段职责

| 数据位置 | 职责 | 是否可作为当前图片 |
| --- | --- | --- |
| `template_payload.editable_payload.variants[0].images` | 当前 SKU/变体图片 | 是，最高优先级 |
| `template_payload.editable_payload.images` | 草稿公共图片 | 是，变体未拥有图片时使用 |
| `template_payload.images` | 模板快照图片 | 是，仅作为兼容回退 |
| `source_images_json` | 草稿保存时的媒体快照及旧数据兼容字段 | 仅作为最后回退 |
| `source_raw.collected_product.images` | 采集来源和审计证据 | 否，不得覆盖当前图片 |
| `manual_facts` / `ai_payload` 中的图片 | 任务事实或历史快照 | 否，不得作为独立权威来源 |

## 3. 唯一解析顺序

后端统一按以下顺序生成 `effective_images`：

1. 当前第一变体拥有的图片；
2. 草稿公共图片；
3. 模板快照图片；
4. `source_images_json` 兼容回退。

“变体拥有图片”包括：

- 变体图片列表非空；
- `images_manually_edited = true`；
- `image_edit_intent = "manual"`。

当用户明确删除了变体全部图片时，空列表也是有效编辑结果，不得回退到采集箱原图。

## 4. AI 裂变继承规则

从草稿裂变新型号时：

- 第 1 张图片可以替换成该目标型号的 AI 新主图；
- 第 2 张及之后的详情图必须来自母草稿当前 `effective_images` 的第 2 张及之后；
- 后端必须根据 `source_draft_id` 再次读取母草稿并校验，不能只信任前端提交的详情图；
- 只要母草稿存在当前有效图片，就不得混入 `source_raw` 或采集箱图片。

目标结构：

```text
[目标型号 AI 新主图, 母草稿当前详情图 1, 母草稿当前详情图 2, ...]
```

## 5. 接口约定

草稿详情和草稿候选接口返回：

- `effective_images`：当前唯一有效图片列表；
- `effective_image_source`：命中来源，例如 `draft_variant`、`draft_editable`、`draft_template` 或 `draft_source_fallback`。

前端、AI 裂变、复制和发布流程应消费 `effective_images`，不得重新合并多个历史图片字段。

## 6. 禁止事项

- 禁止把 `source_raw` 中的采集图片追加到当前变体图片之后。
- 禁止因为当前图片为空就无条件恢复历史原图；必须先判断是否为用户明确删除。
- 禁止新增页面自行定义另一套图片优先级。
- 禁止将视频 URL 写入图片字段。
- 禁止用临时 AI 文件 URL 直接保存可发布草稿。

## 7. 必测场景

每次修改草稿媒体、AI 裂变或发布逻辑时，至少验证：

1. 草稿上传新图片后裂变；
2. 草稿删除全部变体图片后读取；
3. 草稿调整图片顺序后裂变；
4. 旧采集草稿没有变体图片时兼容回退；
5. AI 裂变保留新主图并继承当前详情图；
6. 刷新、重新进入编辑页后图片顺序不回滚；
7. 发布使用的图片与编辑页看到的当前图片一致。

## 8. 故障修复原则

出现图片污染时，应同时检查并修复：

- `source_images_json`；
- `template_payload_json` 中的公共图片和变体图片；
- `manual_facts_json`、`ai_payload_json` 中可能被复制的媒体快照；
- 已生成裂变草稿的详情图。

修复时保留已经生成且确认正确的目标型号主图，只替换被历史来源污染的详情图。
