# 库存三段编号

库存业务编号采用 `核心品名号-汽车品牌号-组内产品序号`，例如 `1-2-15`。三段均为不补零的十进制整数；产品序号从1递增，不设四位长度上限。

`products.id` 是稳定的业务主键，`products.code` 保留旧P码，平台SKU、offer_id和平台条码继续保持原含义。常规迁移只变更 `inventory_number` 及其分类、品牌、序号和版本字段，不重新绑定订单、采购、组件或流水。若用户另有明确确认的历史资料更正，必须逐产品列入审核方案，与改号在同一事务执行。

## 号段规则

- 核心品名首次按活跃真实库存产品数量降序排列，同数量按名称稳定排序。隐藏、退役及已发号选品也纳入迁移和号段占用，但不增加活跃排名数量。
- 品牌首次按活跃真实库存产品数量降序排列，同数量按规范英文品牌名称排序。采用现有品牌别名归一化，不从商品标题或SKU名称推断适配事实。
- 编号一旦发放就冻结。后续销量、产品数、库存件数和排序变化都不会重排号码；新核心品名或新品牌追加号段。
- 核心品名0表示待核对；品牌0表示待核对，品牌1表示明确通用。品牌为空不能直接视为通用；只有明确通用且没有品牌、车型冲突的产品进入通用号段。
- 已知品牌但核心品名缺失的历史产品保留已知品牌，仅使用核心品名0。原品牌、适配类型和车型字段不被迁移工具补猜或清空。
- 相同品名和品牌下，初次按稳定产品ID升序排列序号。之后使用持久计数器。隐藏、删除或改组后不复用已发序号。
- 同组修改名称、颜色、材料、规格、耗材或配件属性，号码不变。变更核心品名或汽车品牌导致实际改组时，生成该组新号，旧号自动保留为历史别名。核心品名字典改名也遵循现有改组语义。
- 继续采用全库唯一号段。企业权限决定可见产品，其他企业不能通过号段或历史别名看到本企业的记录；不能按企业各自从1重复发同一三段号。

V1的 `inventory_number_categories` 及原计数器完整保留。V2使用独立的核心品名表、品牌表和组内计数器，`inventory_numbering_state.version=2` 表示已切换。

## 搜索与旧码兼容

“库存编号精准”支持完整三段新号、历史两段号、旧P码及现有库存ID。旧日报中的数字下划线形式可规范为连字符查询。历史号写入独立 `inventory_number_aliases`，不会冒充产品名称别名，也不能分配给其他产品。

“库存编号前缀”用于查组：`1-2` 或 `1-2-` 表示品名1、品牌2的整组；`1-2-1` 在明确前缀模式下可查以该序号开头的产品。自由搜索中末尾带连字符也明确表示前缀。两段旧号不自动转成新号组，避免把一次旧码精确查询错误展开成几十款商品。

品名、汽车品牌、车型等原有筛选继续可用。前缀限制在数字段边界，例如 `1-2-` 不会匹配 `11-2-` 或 `1-20-`。排序按三段数字顺序，Excel编号列按文本保存。

## 资料编辑和历史查看（2026-11-07）

手机“采购待到货”“到货待验收”的卡片提供“编辑库存”和“历史版本”。资料编辑沿用 `inventory.write` 权限、完整库存表单和原有保存接口，不提交盘点、到货或验收入库操作；保存后刷新当前日期列表并清空旧勾选。修改套装组成仍沿用原有待发订单出库同步，不新增另一套库存计算。采购批次按稳定 `product_id` 打开，不能把批次 ID 当作商品 ID。

“历史版本”也可从电脑库存明细、电脑及手机库存编辑窗口打开；只读入口使用 `inventory.read` 权限，不要求授予资料编辑权。`GET /api/products/:id/edit-history` 返回当前编号、独立留存的旧编号和旧名称，以及按页读取的身份资料修改前后对照、时间和服务端操作人。界面统一显示北京时间。

从本功能启用后，普通库存资料保存与核心品名维护在原事务内追加 `inventory_flow_events.action=product_edit`；旧名称同时保留为 `previous_name` 搜索别名。编号变更继续使用原 V2 触发器的历史号别名，版本快照读取触发器执行后的真实新编号。没有实际身份资料变化不写空版本，失败时修改、别名与历史记录一并回滚。

版本白名单覆盖名称、编号、核心品名、品牌、适配车型、规格、材质、计量单位、尺寸及主档组成等身份资料。它不代表库存余额、采购账或财务快照；组成仅保留当时的稳定商品关联 ID、数量及组成角色，不使用当前名称伪装过去的名称。旧别名的“留存时间”不等于原始修改发生时间，也不能将两个独立别名推断为同一版本。此前未保存完整快照的历史保持明确未知，不倒填、不编造、不自动还原库存。

## 显式迁移

`scripts/migrate-inventory-numbering-v2.mjs` 只接受显式数据库与本机管理员socket或Windows named pipe，不读取应用数据库配置。默认只读。普通结构准备只新增兼容列、表、索引和保留号段，不激活V2，也不改产品编号。

```bash
node scripts/migrate-inventory-numbering-v2.mjs --database=REVIEWED_DB --mysql-admin-socket=/var/run/mysqld/mysqld.sock
node scripts/migrate-inventory-numbering-v2.mjs --database=REVIEWED_DB --mysql-admin-socket=/var/run/mysqld/mysqld.sock --export-plan=/private/reviewed-plan.json
```

导出目录必须存在、位于源码及公开资源之外，并具有私有权限。方案覆盖完整产品源摘要、新旧编号对应关系、企业归属、核心品名和品牌注册表及组内计数器。审阅后添加 `reviewed_by` 与 `reason`，不可删减源字段。工具会重新读取完整源并重建方案，任何新增产品、修改、遗漏、排序篡改或跨产品编号冲突都拒绝执行。

明确确认的资料更正使用纯规划模块的 `identityCorrections` 输入重建完整方案。白名单仅允许名称、核心品名、汽车品牌、适配类型、车型及车型JSON；输出的 `identity_corrections` 和逐款 `identity_updates` 均须与原始源一致。排名和分组使用更正后的资料，源摘要和前值仍保留原值。改名时将旧名称保存到现有历史名称表；已有别名停用或归属异常会拒绝切换，不自动覆盖。仅更正行刷新 `updated_at`，防止旧表单覆盖已审核事实。

正式发布使用已合并的最新release提交，通过部署客户端的 `ReviewedInventoryNumberingManifest`／`--reviewed-inventory-numbering-manifest` 传入私有方案，并明确开启维护窗口。该参数占远端第11位；原第9位生产提交校验、第10位耗材清单保持不变。详见[Ubuntu ECS发布流程](../deploy/linux/README.md)。

执行顺序为：同一发布锁内核对现网提交和方案、完成整库SQL与私有AI结果配对备份并保护恢复点、准备兼容结构、暂停旧主服务和候选写入、再次核对完整源、保存完整产品前像及原触发器定义，再执行事务切换。

切换前安装的V2触发器在版本未激活时拒绝普通写入；仅管理员迁移连接可使用内部会话标志执行审核DML。事务锁定产品，写入冻结注册表、计数器、旧码别名及五个编号字段，应用逐款明确审核的资料更正，复核除此之外的全部产品字段和V1注册表完全不变，最后提交版本2。无核心品名的创建初始空行仍允许存在，结构化资料写入后再发号。

## 失败与恢复

数据事务提交前失败会回滚数据并恢复原发号触发器。若进程在触发器DDL与事务提交之间中断，部署流程必须先用私有前像恢复匹配的触发器代际，成功后才可重启旧服务：

```bash
node scripts/migrate-inventory-numbering-v2.mjs --database=REVIEWED_DB --mysql-admin-socket=/var/run/mysqld/mysqld.sock --apply --writers-stopped --recover=/private/products.before.json
```

版本仍为1时，只在产品编号与前像一致的前提下恢复原触发器；版本已为2时，保留已提交编号并检查或恢复V2触发器。不会把已提交的数据倒回旧号。恢复失败必须保持停写，不能带着未知触发器状态重启旧writer。

切换成功后先验证候选，再切换正式服务。代码回退不会恢复整库或删除别名。旧代码的启动修复不得重装V1触发器或把V2号码改回两段；相应兼容标记和V2启动检查都有真实MySQL测试。

全量备份、配对私有结果、产品前像与触发器定义属于受保护恢复资料，不放入Git、公开下载目录或发布包。整库备份不是业务回退按钮，不能用旧快照覆盖切换后产生的订单和库存操作。
