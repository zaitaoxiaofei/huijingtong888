# 素材优化：一次最终交付、一次客户结算

当前新增了纯阶段契约、准备模块，以及独立的 `main_only` 最终交付协调器。协调器已用隔离 MySQL、真实私有文件和供应商替身验证，但没有接入现有 worker、HTTP 或真实供应商，没有开放生产付费账户。默认企业继续原内部流程。素材优化的付费入口继续由现有门禁拒绝；单张独立图片的既有模块不能被当作完整素材优化收费产品。

## 客户购买的结果

一次已确认的素材优化任务对应一个最终交付：`main_only` 是验收后的主图，`full` 是计划要求的完整图片与文案包。识别、规划、审核及内部重做是完成它的过程，不逐项收客户积分。未来若单独出售识别或审核，需要独立的报价与购买入口；当前没有这类入口。

最终交付编号固定为企业与持久 `batch_no/item_no`，交付范围锁在输入摘要中；改范围必须重新确认，不能悄悄换编号重复收费。重启、自动重试、审核不通过后的候选重做都沿用同一客户报价。候选次数只能增加内部尝试记录，不能产生新的客户账单。明确独立购买的其他交付才允许新报价。

## 本轮可复用内容

- `ai-credit-material-contracts.js` 验证原始供应商 JSON，不接受旧 normalizer 补出来的字段。analysis、plan、review 必须符合已有提示契约；明确的 `review.pass=false` 是有效内部审核结果，并不触发客户扣款。
- 文案复用既有事实契约和复制校验器，要求原回复已包含俄文标题、标签、描述及完整中文译文。现有可靠主体规则仅覆盖雨刮底座、门槛条、钥匙壳和防撞条；其他品类在准备时明确关闭，不能靠通用 fallback 承诺可收费成果。
- `ai-material-stage-preparation.js` 只从已授权加载的持久行准备固定交付编号、来源内容摘要与阶段编号。它不授权请求、不调用数据库、不调用 AI、不冻结或结算积分。调用方仍须核验当前成员、原操作人、源草稿及人工事实。
- 每个内部阶段的 `customerResultCount` 固定为 0。阶段校验返回 `finalDeliveryAccepted=false`，不能直接转为钱包成功回执。图片 URL 不会通过该文本模块的图片验收。

这些结构与词根检查不能证明所有视觉事实或翻译语义正确。现有颜色规则只是 warning；未知品类和没有可靠事实规则的交付仍不能开放。

## 现有执行器为什么不能直接套用

当前执行器适合一个单结果供应商调用：预占、提交、回执查询、结果保存、一次结算。把 analysis、plan、image、review、copy 各包一层执行器会生成多笔独立客户账，导致最终失败仍收取中间步骤费用，因此不可采用。

独立的 `ai-material-delivery-coordinator.js` 实现了这层最小协调逻辑：在一个客户预占内执行多个供应商阶段，保存各自的成本和回执，最终只结算一次。它不能复用浏览器请求体授予底层免费通道，也不能直接嵌套原图片钱包执行器。

## 已完成的独立协调器

- 只支持 `main_only`：识别、计划、候选主图、审核。报价固定在持久企业和 `batch_no/item_no`；只有一笔 `requested_results=1` 的钱包任务和一个 composite attempt。钱包的 `material-item:...` 是内部工作流回执，与 checkpoint 中真实供应商回执分别保存，不能当作上游成功证据。
- 领取在短事务内按企业、item、当前成员和来源归属复核，数据库时钟控制租约，`item.attempts` 作为业务 fencing。等待行锁后重新鉴权；同一 item 的第二个领取者被拒绝。恢复先领取，暂停、取消、原操作人变更、来源移属、订阅或岗位失效都会停止新调用。
- 每阶段先私有保存输入，再提交单调序号、阶段、候选、输入摘要、原上游账号指纹及模型。只有新 marker 可以 POST；重启后没有回执保持待核对，有回执仅允许原账号和模型查询。适配器必须在自己的队列退出、POST 和轮询前调用 `assertAiMaterialDeliveryPermit()`，该上下文来自受信任父钱包任务和原操作人，不接受浏览器跳过计费参数。
- 回执和已知实际成本先保存，可保留撤权或租约过期后迟到的事实；保存事实不会续活过期租约，不会授权下一次调用。未知成本为 NULL，不当零；结算时全部尝试成本已知且单一币种才汇总到钱包 composite attempt，多币种在 checkpoint 分开保留。结算后才迟到的成本仍保存在原 attempt checkpoint，客户账不改变；钱包成本列当前只是结算时投影，后续需要独立幂等成本对账接口，不能把它当作实时完整供应商费用。
- 有效 `review.pass=false` 会沿同一报价增加持久候选序号，前一候选和修正意见继续保存。候选及明确失败重试上限作为原协议策略保留，重启配置变化会暂停原任务。最终必须 `review.pass===true`，并通过真实私有图片归属、原摘要及像素验证；不会仅因 HTTP 200 或 URL 存在而收费。
- 每个阶段先写不可变私有结果再提交检查点。阶段检查点回滚、最终结果已写而结算中断，都可以验证原私有文件恢复，禁止重新 POST。最终恢复直接使用原文件字节，晚到内部成本不能让结果被重新拼装覆盖。成功扣费或失败释放已提交、后置检查点写失败时，恢复会按原钱包终结事实修复检查点，不再次结算，也不推测官方状态。
- 自动结算与平台人工核对交错时，先核对钱包返回状态和 `billing_conflict`。冲突只标为待核对，保留人工账与结果，不宣称已退款或交付成功；后续重放也不会把冲突覆盖为普通成功／失败。人工核定的外部成功结果不等于本协调器已验证的私有最终包，不能据此生成本地交付回执。
- 来源身份包含草稿内容定义和每张有效图片的核验摘要或真正不可变的对象版本。受信任 loader 缺少 `effective_image_identities` 时在预占前返回 `AI_MATERIAL_SOURCE_UNFROZEN`。URL 相同、摘要不同也会暂停原交付。

这是一个依赖注入的服务端模块，没有新表、启动扫描或对外路由。它返回内部交付证据供后续 worker 使用，尚未创建结果草稿，也未把素材 item 伪装为已完成业务交付。

### 待核对与失败的区别

供应商明确拒绝／终止，且原任务仍有执行授权时，可在原报价内有上限地重试；耗尽重试或候选审核均未通过，会释放整笔客户预占。中间已产生的供应商成本由平台承担。

明确完成但文本结构不合格与未知接收分开处理：受信任 adapter 根据实际供应商终态返回 `{status:'succeeded', result}`，或原真实回执查询明确成功，才产生私有 `material-stage-completion-v1` 原始完成证明。坏 analysis／plan／review JSON 会保留证明、回执、成本后在同一报价内有限重试；耗尽后整笔释放，不长期冻结已知失败。证明文件先写而 SQL 中断，也可恢复验证原回复。实际 adapter 不能仅看到 HTTP 200 就臆造终态，更不能接受浏览器传入的这个状态。

超时、未知接收、没有完成证明的坏 JSON、坏私有图片、存储失败和不可核实结果保守待核对，不自动当成明确失败退款。旧 fallback 不会补齐坏结构后收费。中途撤权或取消停止后续调用，预占等待核对或恢复原授权，并不代表已交付或自动退款。这里仍需要面向运营的核对流程。

## 正式接线仍需完成

1. 以持久素材 item 作为协调对象，人工确认范围和价格后，仅调用一次 `ledger.reserve(..., results:1)`。价格版本固定到该客户任务，不为每个过程阶段另建钱包任务。
2. 保留现有素材 item 行锁与领取条件，绑定客户任务 ID、协议版本和原操作人。新协调任务不得自动接管旧的未知提交；旧记录没有协议标记时仍须核对。
3. 扩充现有 `checkpoint_json` 的阶段状态，而不是先新增一组平行业务表。每次调用前保存阶段、输入摘要、单调尝试序号和原供应商账号摘要；返回真实回执后先保存再轮询。较大的原回复放私有结果存储，checkpoint 仅留引用、摘要和必要业务结果，不重复复制类目模板或图片字节。
4. 新增服务端最终交付上下文，仅供已领取的当前 item 使用。它核验已预占的父任务、企业、原操作人、阶段和允许的能力，授权文案、视觉、图片的非结算供应商适配器。所有队列、重试、轮询仍复核当前权限和资源；已有账户不能无父任务走内部额度。
5. 协调恢复必须先取得同一 item 的执行权。只查询原阶段已保存的回执；已完成阶段读持久结果，明确尚未提交的下一阶段才能开始调用。结果未知且没有可核实回执时保持整笔冻结，禁止盲投或换随机编号重做。现有 `provider.query` 的恢复假设不足以保证多阶段推进，需要明确的协调恢复接口及单执行者门禁。
6. 审核失败后若允许内部修正，使用同一最终主图槽位下的持久候选序号；保留旧回执与候选，不创建客户新报价。只有最终选中的候选进入交付结果。独立协调器已具备此门禁，现有素材批次 worker 仍使用旧内部流程。
7. 完整结果通过来源事实、计划要求、图片数量、文件归属、摘要及像素和文案契约后，先持久保存最终结果，再一次性结算 `successfulResults:1`。保存成功而结算中断时，使用现有孤立结果恢复机制并重新验证整包素材。
8. 明确失败且无法完成最终交付时释放整笔预占；中间供应商成本属于平台内部成本。未知结果继续冻结核对；原账已人工结算后，迟到的成本事实不改客户账。同币种费用可汇总，未知费用保留 NULL，不把它当零，也不擅自计算汇率。

现有 image adapter 会自行调用钱包，不能嵌入上述协调层后继续创建子报价。实际文案、视觉和图片非结算适配器尚未接入；它们必须受同一服务端父任务上下文约束。正式私有文件路由还须识别内部 stage task 的企业归属，不能只在内存里声明 owner。

来源媒体摘要目前由受信任 loader 提供。实际适配器必须读取已冻结的私有快照、固定对象版本，或上传前核验真实字节与保存摘要一致；不能把可变 URL 和摘要字段一起传给上游，就宣称内容已被冻结。此项是开放收费的阻断条件。

旧 worker 的启动恢复、领取和重试仍必须显式排除 `final_delivery_v1` 协议 item，或统一改用同一租约／业务 fencing；新协调器尚未接线，不能假定旧进程已经尊重新租约。结果草稿落地与最终交付回执也需在正式 worker 验收，不以钱包结算测试替代。

## 开放前验收

独立协调器真实 SQL 测试 `test/ai-material-delivery-coordinator-mysql.test.js` 已通过 30 项（0 跳过）：并发、重启、阶段及最终私有文件成功但 SQL 失败、账已提交但后置检查点失败的成功／失败对称恢复、人工核定与自动成功／失败交错的账务冲突、人工外部成功不伪造本地交付、租约过期和迟到回执、撤权、业务暂停、来源移属及同 URL 真实文件字节变化、原账号绑定、无回执禁止重投、候选重做同一报价、审核失败释放、余额不足、账户停用及排队后复核、未知结构与确定完成坏 JSON 的区别、账后迟到成本保留而不重扣、图片篡改、默认企业实际数据库身份。替身供应商不产生真实费用，私有图片使用 Sharp 实际解码。

现有默认企业内部流程未修改；独立协调器测试不等于正式 HTTP、实际上游、worker 重启及结果草稿业务闭环已验收。`full`、矩阵、多图及完整文案交付仍不能开放收费。

报价确认、余额与冻结状态界面、真实适配器、旧恢复兼容和最终业务交付验收尚未完成前，不能对外开通付费 AI 账户。本独立模块源码已随 `2026.10.24-priority-a1ef0f7` 部署 ECS，但没有注册进正式 worker 或 HTTP 入口，没有开通生产账户、定价或执行真实收费 AI；部署文件不等于开通业务。测试及后续接线范围如上，不能把根任务其他表的准备迁移当作此协调器已完成交付。
