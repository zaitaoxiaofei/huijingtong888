# 手机财务读取性能

本轮基线为最新 release 的 `45b9854`。用户已明确授权本轮性能修复完成、本地验证通过后合并最新 release、部署 ECS 并验收。

## 读取路径

- 首页财务和月度账单的当前库存资金使用同一可用库存计算。原本对所有有库存流水的产品读取需求时，先展开历史订单的 SKU 配方，再反复查询运输历史和 OGL 实际交运证据。生产只读测量中，这条需求 SQL 用时约 10.1 秒。
- 年度经营总览不读库存，其主要耗时在订单分类。原有报表 SQL 将状态和取消原因的公共文本表达式展开 536 次，导致每条订单重复处理字符串。
- 手机月账单原先等待公司字典和账单两个请求都结束才显示金额，辅助资料慢时延迟了已完成的账单。

## 修复边界

1. 报表通过物化 CTE 复用公共文本、布尔条件。表达式仍来自原有 V1 基础分类和当前分类构造器，不修改已发布公式、订单利润或财务数据；年度、单月和待结算读取使用相同报表分类。
2. 仅本地库存状态读取、产品超过 32 项时，用集合方式读取当前企业订单的运输历史和有效 OGL 实际交运证据，按原有未履约或最近七个完整北京日条件筛选后再展开配方。小产品集合和通用采购分配路径继续使用原有查询。历史状态时间仍取 MIN，NULL 时间与实际交运的租户、店铺、有效成员及撤销校验保持一致。
3. 手机账单完成后立即显示。公司字典独立完成或提示读取失败，并继续核对当前企业、权限、请求代次和取消状态；不改变页面样式和筛选语义。
4. 手机账单明确使用 `includeAppendices=0`，只跳过页面不展示的采购/当前库存资金与 AI 附表。`summary`、`shops`、`expenses`、`shared_expenses` 和订单口径保持，两个附表字段为空对象。未传参数的电脑端、导出与旧客户端继续读取完整附表；公司归属和财务权限仍先校验。

不新增结果缓存、过期时间、数据库结构或生产配置。库存仍为当前可用库存快照；未知可用量不能替换为零，采购与库存占用不重复扣减经营利润。

## 验证与发布

- 隔离且禁用 TCP 的 MySQL：旧版精确函数恢复并校验摘要，与新版逐字段比较年度、月度、待结算完整结果，覆盖默认企业历史 NULL、其他企业、公司/店铺筛选、售后原因、空原因、北京边界、无订单工资和 31,000 条合成订单。
- 库存：大集合新路径与旧查询及工作流完整结果比较，验证配方更改后的冻结出库、历史 MIN/NULL、七日边界、无效或撤销的 OGL 证据、FBP 与安全库存。
- 真实 Chrome 使用本地 8788：375/390/430px、辅助字典延迟或失败、跨企业迟到响应和原有手机日期、月份、权限回归。页面布局保持。
- UTF-8、SQL 绑定、API 文档检查及完整前端构建；源文件与构建产物分别管理。
- 生产验证使用同一只读一致性快照比较旧、新 SQL，业务行和金额仅留内存，输出耗时、数量和等价结果。一次对照的年度查询为 6.81 → 1.36 秒、单月 1.06 → 0.30 秒、待结算 0.66 → 0.26 秒。这是 SQL 样本，不能替代完整页面性能验收。
- 库存最终查询保留运输历史聚合内的企业归属，通过已有覆盖索引顺序读取，并保留 HAVING 物化筛选。生产对照中，738 个产品的完整覆盖读取为 10.52 → 4.07 秒，主需求 SQL 为 8.47 → 2.48 秒；完整结果、Map 和数组顺序均相同。纯计算约 0.28 秒，剩余耗时仍需按完整接口单独测量。
- 从最新精确合并提交执行正式发布，校验预期生产提交以防覆盖并发更新；就绪后分别记录首页财务、经营总览和月账单首次观察及重复请求耗时，并核对月份金额一致与插件包保留情况。
