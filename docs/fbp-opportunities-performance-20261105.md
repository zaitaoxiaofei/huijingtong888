# FBP 备货建议响应与库存名称

基线：`release/2026.10.21-task-brand` @ `666ac3d455b77a709247ebc61e1a882306ce55cc`。本次修复在独立任务分支验证，尚未合并或部署 ECS。

## 问题证据

- 线上普通查询串行测量三次，接口耗时分别为 9.595、6.935、6.521 秒，首字节时间几乎等于总时间；响应约 38KB，JSON 解析约 1–2ms。主要等待发生在服务端。
- FBP 基础商品查询已有企业缓存，但每次翻页、筛选仍通过 `inventoryScopeCoverageMysql` 读取整个企业的产品列表，再重新核算订单、采购和库存占用。
- 原查询将整个企业的产品 ID 列表再次传给覆盖加载器，产生重复产品读取及全产品 `IN (...) OR 历史出库` 条件。
- 抽查返回的 40 行都有 `product_name`。页面库存列只显示编码，漏掉了库存名称；线上商品标题与库存名称是不同字段。
- 页面初始生命周期的相同 GET 已由 API 层合并，不存在已证实的逐行请求风暴。

## 修复范围

- 库存列显示 `product_name` 和原库存编码。未绑定库存、已绑定但未填名称分别明确提示；线上商品标题保留原入口。
- 只为 FBP 建议读取增加短期覆盖结果复用：企业 ID 与默认企业语义共同隔离，20 秒有效期从计算完成开始，库存工作流 revision 改变后失效。
- 相同 revision 的并发读取共享待完成任务。显式 `refresh=1` / `forceRefresh` 绕过已完成结果；失败不缓存，旧任务不能覆盖新 revision 的结果。
- 冷读取使用覆盖加载器的完整企业模式，避免再传整个企业的产品 ID。保留加载器强制 fresh 及企业所有权校验；采购、备货、发货等写入核算仍使用原新鲜读取。
- 保留完整核算后筛选、排序、统计和分页，避免局部核算改变可用库存、建议数量和优先级。
- 只补充已确认影响覆盖结果的成功事务失效通知；不修改库存流水、采购数量、利润或业务状态规则。

失效补点为备货分配、备货数量调整、组件更新、采购申请删除，以及采购单取消、更新、删除。全部在事务成功后执行，提交失败不增加 revision。普通未批准备货编辑、仅新建采购申请不改变本投影，未扩大修改。

## 本地验证结果

- 49 项不同后端专项/相关回归通过，0 失败、0 跳过；另有 1 项真实浏览器测试通过。
- 真实 MySQL 对照默认企业 40 个产品和其他企业 3 个产品，完整覆盖 Map 及附加属性逐项相同。覆盖共享订单、套装组件、SKU 配方、损坏或跨企业映射、历史出库、采购分配、取消运输历史及实际发运/撤销状态。
- 实际 FBP 服务函数的 13 种分页、筛选、搜索和排序请求，旧方式执行 13 次覆盖核算，新方式执行 1 次，返回数据、顺序、统计和名称相同；每次请求仍执行权限复核。
- 7 个写入入口各验证成功提交与提交失败，共 14 项；成功后下次读取重新计算，失败保留上一份成功结果。
- 名称浏览器测试确认真实库存名称和线上商品标题分开，空名称/未绑定分别提示，数量和原操作保留，无外部请求或业务写入。
- 完整前端构建、UTF-8、SQL 绑定、语法及 diff 检查通过。构建仍有原有 `:deep` 和大 chunk 提示，未修改相关页面。
- 未声称全库测试通过。扩展检查发现旧测试问题：`fbp-four-demand-policy` 一条预期与基线不符、`inventory-reservation-boundary` 的 SQLite fixture 缺 `shops` 表，均在未修改的基线复现；另有商品原子更新、订单批次及旧 FBP 路由测试的历史 fixture/断言不匹配，未扩大修复。新增修复的专项验证不依赖这些旧 fixture。

## 验证边界

- 浏览器验证使用本地 `8788`，全部 API 为固定测试数据，并禁止外部网络和业务写入。
- 独立 MySQL 使用随机测试库、named pipe，关闭 TCP；不连接应用数据库或 ECS 数据库。
- 本地合成数据的时间不能作为线上速度承诺。首次读取仍需完整核算；部署后应重新测量实际冷读取及连续翻页耗时。
- 本轮生产调查只做受限只读测量，没有执行刷新、同步或业务写入，没有部署或重启 ECS。
