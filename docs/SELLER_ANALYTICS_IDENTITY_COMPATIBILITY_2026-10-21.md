# 分析插件身份识别与旧版兼容修复

## 排查依据

2026-10-21 的用户诊断日志显示，分析插件 1.0.39 多次在准备分析页时返回 `Navigation rejected.`，随后报告当前店铺身份尚未识别。日志没有提供另一个店铺 ID，不能据此认定用户选错店铺。浏览器拒绝跳转的底层原因仍需现场浏览器证据，不能仅凭这份日志确定。

代码检查发现：

- 新身份校验要求工作线程已经捕获分析请求头。扩展重新加载后内存记录为空，即使正确的分析页已打开，也可能无法继续；准备流程再次跳转失败后，采集队列继续被身份缺失拦截。
- `ozon_company_id` 是插件历史写入的本地缓存。将该缓存和当前 Cookie 不同直接当成店铺冲突，会把旧缓存当成当前店铺证据。
- 页面在旧插件不支持新的实时校验消息时要求最新版，服务端又要求旧协议没有的 `verified_company_id` 和 `current_company_id`，导致增强能力成为旧版采集的硬门槛。
- 更新状态把“版本不同”都当成必须升级，且插件默认 `mandatory: true`，没有区分可选增强与系统级问题。

## 修复边界

- 当前页面与浏览器 Cookie 的实际店铺身份一致时，可以恢复工作线程尚未捕获请求头的上下文；不得用 ERP 期望店铺 ID 冒充实际身份。
- 复用身份已核实的当前分析页。浏览器采集准备与服务器长期授权绑定分别判断，服务器绑定仍需通过授权验证。
- 每次浏览器采集保留实际店铺检查，真实跨店结果仍拒绝入库。缺少可选新字段的旧结果可以通过实际请求的 `X-O3-Company-Id` 校验；缺少实际请求店铺 ID 的结果不得用任务预设值补齐。
- 实时校验消息无响应时回退到原有准备握手，仍要求本次请求完成、插件在线且实际识别店铺一致。身份缺失展示重新识别指引；有实际冲突时才要求检查店铺。
- 保留现有页面模板、布局与样式。

## 更新策略

新增与增强功能默认可选更新；`update_available` 与 `update_required` 分开返回。历史元数据只有 `mandatory: true` 时不构成强制升级依据。

仅同时明确设置 `mandatory: true`、`minimum_supported_version`、`update_reason_type: "system_bug"` 和非空 `update_reason` 时，才对低于最低兼容版本的客户端要求升级。已兼容、版本未知以及比发布版本更高的客户端不应被误要求更新或降级。

分析插件修复源码版本为 `1.0.40`，预期包名为 `ozon-seller-analytics-plugin-1.0.40.zip`。本记录不代表已部署或发布；生产发布仍须检查 ECS 包、更新元数据、下载 URL 与实际下载包内的 manifest 版本一致。

## 验证范围

132 项相关回归全部通过，覆盖当前页面与后台 Cookie 的身份恢复、陈旧缓存、真实跨店阻断、旧版实时消息缺失的握手回退、旧版结果入库、可选更新及系统级最低兼容版本策略。项目编码检查及 Vite 生产构建通过；页面模板和样式与修复前完全一致。Windows 打包已核对包内 manifest 为 1.0.40，版本包与别名包内容一致。

实际用户浏览器的端到端采集需在安装修复包及对应服务端发布后复核。重新加载扩展后，应刷新已打开的 Seller 分析页，使新版页面脚本生效。

Cookie 读取遵循 [Chrome Cookies API 文档](https://developer.chrome.com/docs/extensions/reference/api/cookies)：按标签页所属 Cookie store 与 URL 读取；同名 Cookie 保留 API 返回的第一项，避免后续项覆盖按路径和创建时间确定的优先项。核对日期：2026-10-21。
