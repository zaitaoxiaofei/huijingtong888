# 库存采购总览性能修复

基线：release/2026.10.21-task-brand @ 39d7ba9327c914ba19feb1a40c450e4cd05639dc。此前该版本已部署，线上总览请求超过90秒且用户遇到连接池繁忙。

## 原因与改动

- 总览每40个库存重复读取订单历史和覆盖分配，串行执行；按任务筛选或并发打开页面会再次计算。
- FBP批量库存映射实际上拼接每个商品的子查询，重复扫描映射和线上商品。
- 先为当前企业计算一次完整订单覆盖结果，再以1000个库存分批读取其余证据；大集合使用企业范围查询，避免所有产品ID与历史出库关联OR条件。小集合仍保留精确产品范围。
- FBP映射改为一次集合查询，保留原单商品明细函数作数量对照。套装、配方覆盖、缺失快照和店铺隔离不变。
- 相同企业/商品集合合并并发请求，完整结果缓存20秒；库存工作流revision变化即不复用，手动refresh=1绕过已完成缓存。失败不缓存为零需求；缓存最多8个键。
- 完整核算后筛选和分页保留，保证必须采购、可选保障和统计数量不因先分页而漏算。采购写入和利润公式未变。
- 刷新失败保留上次成功结果并明确标注；初次失败明确“加载失败，不代表没有采购需求”。手动刷新强制重算。

## 验证与限制

115项相关模型、独立MySQL、权限和事件测试通过，0失败/跳过。原单商品FBP映射与新集合查询逐项一致；采购数量、来源、已锁定占用及事务规则回归通过。

独立MySQL合成681个库存和5000条订单：首次约90ms（最终批次调整后以回归日志为准），27次查询，订单历史只读取一次；第二次读取0次查询。该时间仅代表本地合成数据，不能作为生产速度承诺。

实际Vue组件浏览器测试通过：失败提示、保留成功数据、手动强制刷新、企业切换与既有业务入口。前端构建、UTF-8、SQL绑定、API文档检查通过。

生产只读诊断确认681个库存，旧逻辑一次产品集合订单覆盖耗时约20.5秒；旧批次诊断已停止，未写生产数据或修改服务。对待测源码进行生产全量只读对照被自动审批拒绝，理由是此前仅授权独立环境测试及潜在生产负载；未绕过执行。

用户已进一步明确授权受限只读生产对照及验证通过后部署。对照仅使用2连接/SELECT，682个实物库存完整核算约23秒，重复读取0ms且0查询，抽样3个必须采购库存的实物、订单、保障、锁定、可用及采购数量与原逻辑一致。该结果包含生产负载，不承诺冷启动秒开；首次读取仍有进一步优化空间。新修复尚未部署。
