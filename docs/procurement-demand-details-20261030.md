# 采购需求明细与到货跟踪

## 操作规则

- 库存需求总览首次加载后保持当前结果。系统事件只标记“有新变化”，不会轮询、重排或自动刷新。查询、刷新与重新核算由用户主动触发。
- 本地实物与采购在途分列；在途包括已到货待验收货源，不计入实物。三类需求仍按共用货源优先级去重计算。
- FBS明细展示实际待履约订单、3:4商品图、店铺、物流、下单时间、人工备注及货源分配。
- 本地保障展示近7日实际消耗、日均销量、生产及运输周期。人工覆盖允许0，保留自动建议，可恢复自动；修改需要原因、当前版本与审计记录，并作用于同一库存的共用保障规则。
- FBP明细展示正式申请的店铺SKU、申请人、时间与状态。缺口按库存共享池展示；未经仓库分配，不编造每个SKU的缺口。
- 创建采购需求只能选择FBS订单、本地保障、FBP备货申请。缺口成因与需求类型分别记录；说明必填。先核实实物，再按最新缺口提交。已有未采购需求沿用，只增加新增缺口；同一提交标识重复请求不增加数量。

## 采购与仓库边界

- 工作台分为库存需求总览、登记采购、采购到货跟踪。旧登记采购逻辑保留。
- 每次实际采购形成独立批次。同一库存可以同时存在多条未关闭采购；登记后进入到货跟踪。
- 采购人员确认整批到货后退出“未到货”，进入“已到货待验收”。只记录签收，不增加本地实物，不生成成本或库存流水。
- 仓库仍通过既有验货入库流程登记实际验收数量。部分验收后剩余数量继续跟踪；实际入库与成本处理沿用原有事务逻辑。
- 明细与到货接口重新校验企业成员、业务岗位及库存归属。版本变化拒绝过期提交，企业切换清除旧页面数据。

## 库存编辑修复

普通库存编辑此前会强制提交`selection_status=listed`，已有商品状态不一致时触发后端隔离保护。现在普通编辑省略`selection_status`与`product_type`，保留原状态。新建、专门审批及后端非法状态变更保护保留。

## 验证与发布

- 真实Vue浏览器验证：连续通知与推进65秒均不刷新总览；三类明细、人工覆盖、需求提交、采购签收、岗位切换、企业切换、窄屏与暗色模式。
- 独立MySQL验证：多企业隔离、撤权、规则冲突、需求增量与幂等、既有在途覆盖、部分验收、实际采购签收不记库存，以及普通库存编辑保留状态。
- 使用既有设置、事件与到货字段，无新增表。人工保障引入后需求快照算法标识从`demand-v1`更新为`demand-v2`，旧快照首次访问后由原有后台队列重建。
- 本文及开发预览不代表已部署。上线必须基于最新合并release的精确提交构建，并获得本次ECS部署确认。
