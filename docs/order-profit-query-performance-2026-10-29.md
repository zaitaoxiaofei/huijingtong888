# 订单与利润排行查询优化验证（2026-10-29）

## 改动与准确性约束

- 利润排行总数只计算原分组键，保留相同企业、店铺、关键词和北京时间范围。保留产品为空的分组，不使用会丢弃 NULL 分组的 COUNT(DISTINCT product_id)。金额查询、售后分类、广告补充、利润版本和舍入逻辑保持原样。
- 物流先限定日期/店铺范围并聚合订单 ID 与计费规则名称，再关联完整原始 JSON。保留原规则顺序、缺失规则、原始物流证据和 FBP 分类，避免宽 JSON 进入分组临时表，也避免小日期范围仍汇总全部历史。
- 订单未绑定状态用企业范围内的去重关系代替逐订单的相关绑定查找；保留直接绑定、SKU 回退、停用产品和默认企业 NULL 归属的原有判定。
- 合并请求中的物流与采购覆盖读取并行开始。采购覆盖仍使用现有的实时、企业隔离算法，没有增加过期库存或采购缓存。
- 一次物流汇总只构造一次规则哈希前缀，逐订单使用 hash.copy()；新旧缓存键逐一完全一致，配置变化仍改变缓存键。

真实生产数据只做 SELECT 对照：同一只读一致性快照中，2026-10-28 范围的 SKU/店铺/产品排行完整返回值哈希及 178 个物流结果完全相同；修正后的窄范围物流 SQL 约 228.68→73.94 ms。第一次不限制日期的原查询触发 20 秒诊断上限，停止该轮并改为日期受限复核；没有通过放宽超时来掩盖问题。这个复核只证明所选范围，不冒称已比对所有历史参数组合。
