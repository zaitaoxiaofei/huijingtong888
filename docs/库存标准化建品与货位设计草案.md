# 库存标准化建品与货位设计草案

## 文档目的

本文档记录库存商品创建、标准名称、结构化字段、套装组成和货位管理的业务规则，作为后续数据库、接口和 UI 改造的共同依据。

当前目标不是增加更多填写项，而是减少自由输入、降低误填概率，并让库存名称、查重指纹、SKU 绑定、套装扣减和仓库拣货使用同一套结构化数据。

## 已确认的设计方向

### 1. 不增加“使用场景”字段

系统当前主要管理汽车相关产品，“车载”等使用场景区分价值有限，新增该字段只会增加操作负担。

例如“车载香薰”应规范为：

- 核心品名：香薰
- 汽车适配：通用，不限制汽车品牌和车型
- 其他物理差异由材质、工艺、颜色和款式表达

### 2. 创建页面分为三个业务区段

页面按操作顺序分成三个区段，每个区段顶部必须有一段短说明，解释字段用途、填写边界和常见错误。

区段建议为：

1. 产品身份
2. 规格属性
3. 库存计量与履约

货位信息可作为第三段中的独立行，也可以在 UI 空间不足时单独形成“仓储位置”区段，但业务顺序仍位于产品组成确认之后。

## 第一段：产品身份

### 区段说明建议

> 用于确定这是什么产品，以及适配哪个汽车品牌和车型。核心品名只填写商品本身，不要加入品牌、车型、材质、颜色和数量。

### 字段排布

第一行放置：

- 核心品名
- 汽车品牌，可不填
- 车型，可多选且可不填

取消商品品牌字段，不再要求用户判断产品自身品牌。汽车品牌和车型只表达适配关系，均放在产品身份区域的第一行。

### 核心品名

核心品名只表达商品本体，是标准化产品名词。

正确示例：

- 香薰
- 钥匙壳
- 门槛条
- 防滑垫

不正确示例：

- 车载香薰：应改为“香薰”
- 吉利钥匙壳：品牌应放入汽车品牌
- T4L 门槛条：车型应放入车型
- 黑色防滑垫：颜色应放入颜色

继续保留最多 7 个字的限制。核心品名使用受控下拉，不允许普通用户直接创建正式选项。

### 汽车适配品牌和车型

汽车适配品牌和车型只描述产品适用于哪些车辆，不表示商品自身品牌。该数据复用 AI 裂变模块已有的汽车品牌、车型数据，不再维护第二套重复字典。

汽车品牌和车型都允许不填，不再增加“通用/专用”单独选项：

- 汽车品牌、车型都不填：适配范围为“通用”。
- 选择汽车品牌、车型不填：适配该汽车品牌全系，标准名称显示汽车品牌，不显示“通用”。
- 选择汽车品牌并选择一个或多个车型：适配指定车型。
- 不允许只选择车型而没有汽车品牌。

非汽车类产品同样可以把汽车品牌和车型留空。为避免名称出现没有业务意义的“通用”，建议由核心品名配置一个 `automotive_fitment_enabled` 属性：汽车适配类核心品名在空值时显示“通用”，非汽车类核心品名在空值时不显示适配文字。该属性由有字典维护权限的人员配置，不增加普通用户的填写步骤。

交互规则：

- 先选择汽车品牌，再加载该品牌下的车型。
- 车型支持多选，以标签展示已选车型。
- 支持搜索和批量识别，例如输入 `T4 T4L`、`T4,T4L` 或 `T4/T4L`，识别为两个车型候选。
- 品牌或车型使用稳定 ID 保存，展示名称只用于界面显示。
- 通用汽车用品应根据品牌和车型空值推导，不通过创建一个名为“通用”的假汽车品牌或假车型实现。
- 普通用户不能临时创建品牌或车型。

需要在开发前核对 AI 裂变模块的数据源、主键和停用状态，确保库存模块只引用，不复制字典。

## 第二段：规格属性

### 区段说明建议

> 用于区分实物规格。材质、工艺和颜色必须从标准选项中选择；款式只填写无法由其他字段表达的外观或版本差异。

### 字段排布

同一行放置：

- 材质
- 工艺
- 颜色
- 产品款式

示例：

- 材质：TPU，也可以不填
- 工艺：可以不填
- 颜色：黑色
- 产品款式：无 Logo；不填时自动使用“普通”

### 字段规则

材质、工艺和颜色使用受控下拉：

- 必须保存标准选项 ID，不直接依赖显示文字。
- 支持搜索已有选项。
- 材质和工艺允许留空，留空表示不参与标准名称，不需要再选择“无”。
- 颜色别名需要归一化，例如“黑”“纯黑”在录入时映射到标准颜色“黑色”。
- 普通用户不能通过 `allow-create` 直接增加选项。

产品款式允许开放输入，典型内容包括：

- 无 Logo
- 普通款
- 带 Logo
- 小怪兽款

产品款式允许不填。保存和生成指纹前将空值规范化为统一的默认款式“普通”，避免空值、“普通”和“普通款”成为三个不同产品。

产品款式不应重复填写品牌、车型、材质、工艺、颜色或数量。保存前可增加跨字段提示，例如款式中出现已知品牌名称时提示用户修改。

### 字典维护权限

以下用户允许创建和维护核心品名、材质、工艺、颜色等受控选项：

- 当前业务负责人本人
- 动力牛马

其他用户：

- 可以搜索和选择已启用选项。
- 不显示“新增选项”入口。
- 不允许通过直接输入、接口调用等方式创建正式选项。
- 如果确实缺少选项，后续可以增加“申请新增”流程，但申请不能立即进入正式字典。

权限必须同时在前端和后端校验，不能只隐藏按钮。开发时应使用人员 ID 或正式权限标识，不应仅依赖容易变化的显示名称。

## 第三段：库存计量与履约

### 区段说明建议

> 用于确定库存如何计数、该产品能否作为其他产品的配件，以及出库时是直接取货还是按组件组装。

### 数量和单位

- 原“包装”字段改名为“数量”。
- 数量必须为正数，默认值为 1。
- 单位必须填写。
- 单位使用受控下拉，例如个、件、套、对、条、片、盒、包、瓶、支。
- 数量与单位属于库存身份的一部分，例如 `1 个` 与 `2 个装` 不能被系统视为同一个库存商品。

### 单品与配件角色

用户可以勾选：

- 可作为单品销售
- 可作为其他产品的配件

这两个角色允许同时选中。例如一个香薰补充片既可以单独销售，也可以作为香薰礼盒的组件。

这两个选项表达的是产品用途角色，不用于判断是否为套装。

建议保存为两个独立布尔字段或角色关系，不使用互斥枚举：

- `can_sell_individually`
- `can_be_component`

### 单品与套装的判定

套装不再由用户手工选择“单件/套装”，而是由产品组成自动推导：

- 没有子产品：单品。
- 添加一个或多个子产品：自动成为套装。
- 删除全部子产品：恢复为单品。

一旦添加子产品，界面展示套装名称后缀设置。标准名称由基础名称与套装后缀自动组合。

示例：

- 基础名称：`香薰 通用 黑色 普通 1个`
- 套装后缀：`礼盒套装`
- 最终名称：`香薰 通用 黑色 普通 1个 礼盒套装`

如果组件中存在礼盒或包装盒，系统可以推荐“礼盒套装”后缀，但是否自动采用应以明确的组件类型或套装模板为依据，不能仅靠组件名称包含“礼盒”二字判断。

### 套装组成

套装必须结构化选择子产品和数量，不能只手写“套装内容”。每一项至少包含：

- 子产品 ID
- 数量
- 单位
- 组件角色，例如主体、配件、包装、赠品

套装名称、库存扣减、分拣任务和打包清单都应读取同一份产品组成数据。

## 产品标准名称与唯一指纹

### 空值显示原则

界面必须区分“未填写”“无”和“通用”，不能都用空白、横线或“默认”代替：

- `未填写`：用户尚未提供该信息，不能推断该属性不存在。
- `无`：已经确认产品确实没有该属性，只在业务需要明确区分时作为正式字典值。
- `通用`：已经确认不限制汽车品牌和车型，是明确的适配结论。
- `默认`：只描述系统行为，不是产品属性，不应出现在库存名称、详情或下拉选中值中。

各字段的具体显示规则：

| 字段 | 创建表单初始显示 | 保存后的详情显示 | 标准名称 |
| --- | --- | --- | --- |
| 核心品名 | `请选择核心品名` | 必填，不存在空值 | 必须显示 |
| 汽车品牌、车型 | `不选择则为通用` | 汽车适配类显示`通用` | 汽车适配类显示`通用` |
| 颜色 | `请选择颜色（可不填）` | `未填写` | 留空时不显示 |
| 款式 | 直接预选`普通` | `普通` | 显示`普通` |
| 材质 | `请选择材质（可不填）` | `未填写` | 留空时不显示 |
| 工艺 | `请选择工艺（可不填）` | `未填写` | 留空时不显示 |
| 数量 | 默认填入 `1` | 显示实际数量 | 必须显示 |
| 单位 | `请选择单位` | 必填，不存在空值 | 必须显示 |

汽车品牌和车型空值只有在核心品名属于汽车适配类时才解释为“通用”。非汽车类产品不显示汽车适配字段，也不在名称中增加“通用”。

颜色、材质和工艺留空只能解释为“未填写”，不能自动显示为“无”。如果未来业务确实需要表达“无工艺”等明确事实，应在对应字典中选择正式选项“无”，而不是由空值推导。

款式采用真正的表单默认值：创建表单打开时直接选中并保存“普通”，而不是让数据库保持空值、仅在页面临时显示“普通”。用户改成“无Logo”等款式后，以用户选择为准。

### 标准名称

标准名称只由结构化字段生成，用户不能直接修改最终名称。固定顺序为：

`核心品名 + 汽车适配范围 + 颜色 + 产品款式 + 材质 + 工艺 + 数量单位 + 套装后缀`

示例：

`钥匙壳 大众 T4/T4L 黑色 无Logo TPU 拉丝 1个`

字段为空时按以下规则处理：

- 汽车品牌和车型都为空：汽车类产品显示“通用”；非汽车类产品不显示适配文字。
- 颜色为空：不显示，但保存前应根据业务决定是否允许无颜色产品。
- 产品款式为空：显示并保存为“普通”。
- 材质为空：不显示。
- 工艺为空：不显示。
- 数量和单位：始终显示，单位必须填写。
- 车型多选：按车型字典的稳定顺序显示，使用 `/` 连接，例如 `T4/T4L`，不使用用户的选择先后顺序。

空字段和标准值“无”是否显示，需要按字段制定固定规则。例如工艺为“无”通常不必出现在名称中，但其标准 ID 仍应进入查重判断。

### 唯一指纹

唯一指纹用于识别是否为同一个真实库存商品，与数据库永久 ID、展示名称相互独立。

建议参与指纹的字段：

- 核心品名 ID
- 是否属于汽车适配类核心品名
- 汽车适配状态，由品牌和车型字段推导
- 汽车品牌 ID
- 排序后的车型 ID 集合
- 材质 ID
- 工艺 ID，空值使用统一的空标记
- 颜色 ID
- 规范化后的产品款式，空值、“普通”和“普通款”统一为“普通”
- 数量和单位 ID
- 套装组成及每个组件数量
- 套装履约方式

车型多选和组件列表在生成指纹前必须按稳定 ID 排序，避免相同内容因选择顺序不同生成不同指纹。

保存前先精确匹配唯一指纹，再展示语义相似产品。指纹完全一致时原则上不允许新建，只允许绑定已有库存品。

## 仓库位置与套装履约

### 核心原则

货位不应只保存为产品主档上的一个文本字段。一个库存品可能位于不同仓库、库区或货位，因此位置关系应至少表达：

`库存品 × 仓库 × 货位 × 可用数量`

### 单品

单品直接维护自身货位。拣货时从该库存品有可用数量的货位生成任务。

### 套装需要区分两种履约方式

#### 预装套装

套装已经提前组装并作为一个完整库存单位存放：

- 套装拥有自己的库存数量和货位。
- 组装入库时扣减组件库存并增加套装库存。
- 订单出库时直接从套装货位拣货。
- 不再临时前往各组件货位重复拣货。

#### 按单组装

套装平时不预装，收到订单后现场组合：

- 套装本身不维护可用库存和固定货位。
- 可销售数量由各组件可用库存共同计算。
- 拣货任务按组件拆分，可能需要前往多个货位。
- 拣齐后送往一个组装台或打包台完成组装。

因此，添加子产品后除了自动判定为套装，还必须选择履约方式：

- 预装库存
- 按单组装

这个选择会直接影响库存扣减、可售数量、货位展示和分拣路径，不能只靠是否填写套装位置推断。

### 创建页面中的位置行

建议位置行显示：

- 仓库
- 库区
- 货位
- 默认上架位
- 默认拣货位

交互规则：

- 单品：显示自身默认货位。
- 预装套装：显示套装自身货位。
- 按单组装套装：提示“无需填写套装货位，出库时将前往各组件货位拣货”，并显示各组件当前默认货位摘要。
- 新产品尚未分配货位时允许保存主数据，但应进入“待分配货位”状态，不能把空值误认为没有仓储要求。

未来如果一个库存品允许多货位存放，应在库存详情或上架流程维护完整货位余额；创建页面只负责设置初始或默认位置，不承担全部库存分布管理。

## 权限与审计

需要受控的操作包括：

- 新增、编辑、停用核心品名。
- 新增、编辑、合并材质、工艺和颜色。
- 修改汽车品牌、车型引用关系。
- 合并重复库存品。
- 修改已有套装的组件组成和履约方式。

这些操作应记录操作人、修改前内容、修改后内容和北京时间。已经产生库存流水或被订单引用的结构字段，不能直接静默修改；必要时创建新变体或走受控合并流程。

## 开发前仍需确认的问题

以下问题不影响当前总体设计，但实现前需要最终确定：

1. 非汽车类产品是否通过核心品名配置自动隐藏汽车品牌和车型。建议隐藏，减少视觉负担，但不增加用户操作。
2. 是否需要支持一个产品适配多个汽车品牌。第一版建议暂不支持；确有需求时再将汽车品牌升级为多选。
3. 颜色为空时是否允许保存。建议部分产品允许为空，不要为了指纹完整强制用户随便选择颜色。
4. 预装套装是否允许拆套回组件库存，以及由哪些角色操作。
5. 新建产品是否必须立即分配货位。建议允许进入“待分配货位”，但在正式入库前必须完成分配。
6. AI 裂变汽车品牌和车型数据是否具备稳定主键、启停状态和别名。如果没有，需要先补齐再供库存模块复用。

## 推荐实施顺序

1. 统一字段定义与字典权限，复用 AI 裂变品牌车型数据。
2. 改造创建页面三段式布局和动态说明。
3. 增加材质、工艺标准字典及颜色归一化。
4. 将车型改为基于稳定 ID 的多选。
5. 建立标准名称生成器和唯一指纹查重。
6. 统一子产品组成，自动推导单品或套装。
7. 增加预装库存与按单组装两种履约方式。
8. 建立仓库、库区、货位关系和待分配流程。

## 统一库存搜索与选择规则

### 设计目标

库存列表搜索、订单绑定库存、绑定子产品以及后续套装组件选择，必须共用同一个搜索接口、字段归一化规则和结果排序逻辑，不能在各页面分别实现模糊搜索。

前端建议复用一个统一的“库存选择器”组件，根据使用场景传入筛选限制：

- 库存列表：允许搜索全部库存商品。
- 订单绑定库存：优先展示可单独销售、状态正常的库存商品及套装。
- 绑定子产品：优先展示允许作为配件的商品，排除当前产品自身，并阻止循环组成。
- 套装组件选择：显示组件货位、可用库存和是否缺货。

### 两种搜索模式

#### 默认快速搜索

保留一个主搜索框，用户可以直接输入自然顺序的关键词，例如：

- `钥匙壳 大众 T4 黑色`
- `大众 T4 T4L 无Logo`
- `钥匙壳 黑 TPU`
- `礼盒套装`

后端对输入执行以下处理：

1. 统一大小写、全角半角、空格和常见标点。
2. 将逗号、斜杠、顿号和连续空格作为候选分隔符，但保留 `T4L`、`无Logo` 等完整词。
3. 使用标准字典及别名识别核心品名、汽车品牌、车型、颜色、材质和工艺。
4. 将“黑”归一化为“黑色”，“普通款”归一化为“普通”等标准值。
5. 已识别字段按结构化字段查询，未识别词继续匹配标准名称、款式和历史别名。
6. 多个关键词默认使用 AND 语义，即结果应尽量同时命中全部关键词，而不是命中任意一个就出现。

搜索框下方可以用小标签展示系统的解析结果，例如：

`核心品名：钥匙壳` `汽车品牌：大众` `车型：T4` `颜色：黑色`

用户可以删除误识别标签，剩余文字继续作为自由关键词搜索。

#### 精确筛选

用户点击“精确搜索”后展开结构化条件，字段顺序与创建库存保持一致：

```text
[核心品名] [汽车品牌] [车型多选]
[颜色] [款式] [材质] [工艺]
[数量] [单位]
[产品角色] [产品组成] [履约方式] [仓库/货位]
```

规则如下：

- 未选择的筛选条件表示“不限制”，不能解释为产品字段为空。
- 选择汽车品牌但不选车型时，搜索该品牌全系及符合规则的指定车型产品。
- 选择多个车型时，默认匹配包含任意所选车型的产品；提供“必须同时适配全部车型”的高级开关没有明确需求前不实现。
- 搜索“通用”时只匹配汽车适配类且品牌、车型为空的产品，不匹配所有非汽车类产品。
- 款式搜索对“普通、普通款、默认款”先做别名归一化。
- 数量和单位组合查询，不能只按名称字符串匹配 `1个`。

### 搜索索引字段

每个库存商品保存一份用于搜索的规范化文本，但结构化查询仍使用独立字段或关联表。

建议搜索文档包含：

- 库存永久编码
- 标准名称
- 核心品名及别名
- 汽车品牌名称及别名
- 所有车型名称及别名
- 颜色、材质、工艺的标准名称及别名
- 规范化款式
- 数量和单位
- 历史名称
- SKU、Offer ID、条码和制造商料号

当主数据、别名、车型或套装组成发生变化时，必须同步更新搜索文档。唯一指纹用于精确查重，搜索文档用于查找，两者不能混为同一个字段。

数据量在当前规模下优先使用 MySQL 结构化索引、关联表索引和预计算搜索字段，不需要立即引入独立搜索引擎。避免在查询时对大量行执行多个前置 `%关键词%` 条件；先通过结构化字段和映射表缩小候选集，再对候选执行名称或别名模糊匹配。

### 搜索结果排序

统一采用分层排序：

1. 库存编码、SKU、条码完全一致。
2. 唯一指纹或全部结构字段完全一致。
3. 核心品名、汽车品牌、车型、颜色等全部关键词命中。
4. 标准名称前缀或完整短语命中。
5. 历史名称和别名命中。
6. 仅部分关键词命中。

同一匹配等级内，再按业务场景排序：

- 订单绑定：有可用库存、最近绑定过、可单独销售的产品优先。
- 子产品绑定：允许作为配件、有可用库存、最近使用过的组件优先。
- 库存列表：默认按匹配度，再按最近更新或现有页面排序规则。

不要简单按使用次数把不准确结果排到精确结果前面。

### 搜索结果展示

搜索结果不能只显示一条拼接名称。每一项建议展示：

- 主图和标准名称。
- 库存编码。
- 核心品名、汽车品牌/车型、颜色、款式等结构化标签。
- 可单独销售、可作为配件、单品、预装套装或按单组装等状态。
- 当前仓库可用库存和默认货位。
- 命中原因，例如“车型和颜色匹配”“历史名称匹配”。

订单绑定时额外展示该库存品已经绑定的店铺和 SKU 数量，帮助用户判断是不是已有的共享库存品。绑定子产品时额外展示组件角色和默认用量输入框。

### 不同绑定场景的约束

#### 订单绑定库存

- 可以绑定单品、预装套装或按单组装套装。
- 高度疑似相同的库存品并排出现时，突出标准主数据和已有绑定数量。
- 默认不展示停用、待合并或缺少必要结构字段的历史脏数据；需要时通过“包含历史数据”筛选查看。

#### 绑定子产品

- 默认只展示 `can_be_component = true` 的库存品。
- 提供“显示其他库存品”入口，但绑定前提示其尚未标记为可作为配件。
- 排除当前父产品。
- 后端必须检测循环依赖，例如 A 包含 B 时，不能再让 B 包含 A。
- 套装是否允许继续作为另一个套装的子产品需要统一规则。第一版建议允许展示但禁止选择，优先只使用原子单品作为组件，减少多层扣减复杂度。

### 旧数据兼容

历史产品结构字段不完整时：

- 保留旧名称作为历史别名，确保仍然可以搜索到。
- 搜索结果明确标记“待规范”。
- 用户绑定前可以查看旧名称和已有 SKU 绑定关系。
- 不允许搜索过程自动修改历史库存品。
- 主数据管理员完成结构化和合并后，旧名称继续作为别名保留。

### 建议接口边界

统一接口应接受：

- `query`：默认快速搜索原文。
- 核心品名、汽车品牌、车型 ID 列表。
- 颜色、款式、材质、工艺。
- 数量、单位。
- 产品角色、套装类型和履约方式。
- 仓库、货位和库存状态。
- `context`：`inventory`、`order_binding` 或 `component_binding`。

接口返回统一库存商品结构，并附带：

- 匹配得分。
- 命中字段和命中原因。
- 标准化后的查询标签。
- 是否可以在当前场景选择及不可选原因。

前端只负责展示和提交筛选条件，不能在不同页面各自重新计算匹配得分或判断循环组成。
