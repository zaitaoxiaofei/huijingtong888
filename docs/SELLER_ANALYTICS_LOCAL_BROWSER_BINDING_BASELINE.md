## 已验证能力

- ERP 可为每个 `tenant_id + store_id` 创建独立的 Ozon 登录浏览器目录。
- 用户在本机打开登录窗口、登录正确店铺并点击“确认长期绑定”后，后端保存 Playwright `storageState` 授权快照。
- 后台同步从授权快照创建独立无界面浏览器，不依赖用户继续打开登录窗口。
- 同一店铺的并发浏览器启动使用单飞锁，避免多个 Chrome 抢占同一个配置目录。

## 当前实现流程

1. 前端数据分析页面请求 `browser-profile/prepare`。
2. 后端在当前运行服务器启动一个可见 Chrome，打开 Ozon Seller 分析页面。
3. 用户在该 Chrome 中登录并选择正确店铺。
4. 前端请求 `browser-profile/confirm`。
5. 后端通过 `sc_company_id` 校验 Ozon 当前店铺 ID 与 ERP 店铺 ID。
6. 校验成功后保存：
   - `erp-profile.json`：店铺确认标记、确认时间、最后成功时间和错误摘要。
   - `erp-auth-state.json`：Playwright Cookie 和页面存储状态。
7. 后台定时任务读取授权快照，使用 Playwright 管理的隔离浏览器执行 Ozon分析请求。

## 当前限制

- 可见 Chrome 启动在后端服务器。开发环境中前端和后端位于同一台 Windows 电脑，因此用户可以操作；直接迁移到无桌面的 ECS 后，用户无法看到该登录窗口。
- 授权快照当前是服务器本地文件，不会自动从开发电脑迁移到 ECS。
- 如果 ECS 更新覆盖上传目录、容器使用临时文件系统或没有挂载持久云盘，授权快照会丢失。
- 当前授权快照文件包含敏感 Cookie，不能写入 Git、日志、普通备份包或 AgentMemory。
- Ozon可能因出口 IP、设备环境、会话过期或风控返回 401/403，需要重新绑定或远程登录兜底。
- 旧版本只写入 `erp-profile.json`，没有 `erp-auth-state.json`；这类记录页面曾显示“已绑定”，但服务重启后无法恢复。

## 下一阶段改造边界

下一阶段计划改为：用户在本地 Ozon浏览器完成登录，由分析插件读取必要会话，通过 HTTPS 上传到 ERP/ECS；ECS 后端验证店铺 ID、加密保存授权并供夜间任务使用。

开始改造前需另外确认：

- 分析插件的可维护源码位置和打包流程；
- ECS授权加密方案（优先阿里云 KMS，备选 AES-256-GCM 加环境密钥）；
- 授权表结构与租户/店铺唯一约束；
- 插件上传接口的身份认证、权限控制、防重放和日志脱敏；
- Ozon会话是否能跨本机与 ECS出口 IP 使用；
- 跨环境验证失败时的远程 ECS浏览器兜底方案。

## 2026-08-06 插件会话上传实现

当前实现已改为优先复用商品采集插件的本地会话上传能力：

1. 用户在自己的浏览器登录目标 Ozon Seller 店铺。
2. ERP发起“重新识别店铺”后，插件校验当前 `company_id` 与 ERP店铺 ID。
3. 插件把 Cookie 会话、结构化 Cookie 元数据、插件版本和采集时间通过 ERP现有鉴权接口上传。
4. 后端先用 Ozon分析接口验证会话；验证成功后才绑定店铺。
5. Cookie 和结构化 Cookie 使用 AES-256-GCM 加密后写入 MySQL `settings`，数据库中不再保存明文 Cookie。
6. 旧明文绑定首次读取时自动迁移为密文，不清空、不覆盖其他店铺记录。
7. 成功绑定不再因固定 7 天 TTL 自动失效；只有 Ozon真实返回 401/403 时才标记失效并要求重新绑定。
8. 数据分析同步和商品采集号池共用同一解密能力，避免一处升级后另一处无法读取。

ECS必须配置稳定的 `SELLER_ANALYTICS_AUTH_ENCRYPTION_KEY`，建议使用至少 32 位随机值。该密钥不得提交到 Git、日志、普通备份或前端代码，并且在服务重启、重新部署和多实例之间保持一致。若密钥变化且旧密钥不可用，已保存会话无法解密，需要店铺重新绑定。

本方案不保证 Ozon会话永久有效。Cookie 自身过期、账号主动退出、风控或出口 IP策略仍可能导致 401/403；此时系统会保留失效状态和错误摘要，由用户重新上传会话。
